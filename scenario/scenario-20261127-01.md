# scenario-20261127-01：网约车实时派单：司机位置索引、批量匹配与防重复派单

## 一、题目

**业务背景**：城市出行平台的旧系统把每个城市的司机位置放在一个 Redis GEO key 里，乘客下单后向附近司机广播抢单。高峰期出现大城市单分片 CPU 打满、一个司机同时收到多张单、Redis 主从切换后一个订单被两个司机接走、近处司机抢不到而远处司机接单导致接驾时间长。现要求重新设计派单系统。

**需求约束**

- 运力：全国同时在线司机峰值 100 万，每 4 秒上报一次位置，即 25 万 QPS（突发 30 万）。
- 订单：日均 2000 万单；下单峰值全国 3000 单/s，最大单城 600 单/s。
- 读：乘客首页"附近车辆"查询峰值 5 万 QPS，P99 < 100ms，允许 2~3 秒旧数据。
- 时延：下单到司机收到派单 P99 < 3s（含批量匹配窗口）；司机应答超时 15s。
- 匹配：半径 3km 起，按等待时间扩到 5km、8km；60 秒无可用司机则结束订单。
- 一致性：一个司机同一时刻最多一个待应答派单或进行中订单；一个订单最多一个司机接单成功；Redis 故障或切主时也不能破坏。位置数据允许秒级延迟和少量丢失。
- 可用性 99.95%，单城市故障不扩散。
- 范围外：拼车、连环单、计价与支付。司机只匹配起点在其营运城市内的订单。

## 二、整体架构

```
[位置链路]

  Driver App --(long conn: location.report)--> Access Gateway
                                                    |
                                                    v
                                            Location Service        校验、漂移过滤、算 H3 格子
                                              |           |
                                              v           v
                                   Redis Geo Index     Kafka driver_location (key=driver_id)
                                   drv:<driverId>              |
                                   geo:<city>:<cell>           v
                                         ^   ^          ClickHouse driver_trajectory
                                         |   |
[附近车辆]                               |   |
  Passenger App --> Nearby Service ------+   |          按父格子路由 + 本地缓存 2s
                                             |
[下单与派单]                                 |
  Passenger App --> Order Service            |
                         | local tx: ride_order + outbox
                         v                   |
                    MySQL (sharded by city)  |
                         | outbox relay      |
                         v                   |
                  Kafka dispatch_request     |
                         | partition = region|
                         v                   |
                  Dispatch Engine -----------+          etcd 租约认领区域, 1.5s 一批
                    |    |    |
                    |    |    +--> ETA Service          批量路网接驾时间
                    |    |
                    |    +--> matching (bipartite graph)
                    |
                    v
           MySQL tx: order CAS + driver CAS + offer + outbox      唯一权威
                    |
                    v
           Push Service --> Access Gateway --> Driver App
                                                    | accept / reject
                                                    v
                                            Order Service (CAS tx)

[超时与补偿]
  Delay Queue + DB sweeper --> offer 超时回退 --> 订单重回待匹配
```

**核心分工**：Redis 只存可丢可重建的软状态（位置、状态提示）；订单与司机占用状态只以 MySQL 为准。订单、司机运行态、派单记录按 city_id 同分片，派单和接单都是单库本地事务。

**容量估算（单机吞吐为假设值，上线前须压测）**

- 位置写：每次上报 1 次 Lua（司机 hash）+ 1 次 ZADD，约 5% 跨格再加 1 次 ZREM（30km/h 时 4 秒约走 33 米），合计约 51 万次调用/s。按单主节点 6 万次/s 需 9 个主节点，部署 16 主 16 从。内存占用不到 1GB，瓶颈在 CPU。
- Kafka：25 万条/s x 约 200B = 50MB/s，按峰值保留 24 小时、3 副本约 13TB，按均值减半估算约 6.5TB。
- 批次规模：最大城市 600 单/s x 1.5s = 900 单，切成约 8 个区域，每区域百级订单，求解为毫秒级。
- 时延预算：等窗口 1500ms + 召回 100ms + ETA 200ms + 求解 100ms + 提交与推送 500ms = 2.4s。
- MySQL：全国峰值写事务约 1.5 万 TPS，16 个分片（1 主 2 从），最大城市独占分片（约 3000 TPS）。订单 2000 万/天 x 约 1KB = 20GB/天，在线保留 90 天约 1.8TB，更早归档。

## 三、数据库表设计

```sql
-- 以下三张业务表 + outbox 位于同一城市分片; order_id / offer_id 内嵌分片号用于路由
CREATE TABLE ride_order (
  order_id          BIGINT UNSIGNED NOT NULL,
  request_id        VARCHAR(64)     NOT NULL COMMENT '客户端幂等键',
  passenger_id      BIGINT UNSIGNED NOT NULL,
  city_id           INT UNSIGNED    NOT NULL,
  region_id         INT UNSIGNED    NOT NULL COMMENT '派单区域, 由起点计算',
  car_type          TINYINT         NOT NULL,
  pickup_lat        DECIMAL(10,7)   NOT NULL,
  pickup_lng        DECIMAL(10,7)   NOT NULL,
  dropoff_lat       DECIMAL(10,7)   NOT NULL,
  dropoff_lng       DECIMAL(10,7)   NOT NULL,
  status            TINYINT         NOT NULL DEFAULT 10
    COMMENT '10匹配中 20待应答 30已接单 40已到达 50行程中 60完成 90取消 91无车',
  current_offer_id  BIGINT UNSIGNED NULL,
  driver_id         BIGINT UNSIGNED NULL COMMENT '接单成功后写入',
  version           INT UNSIGNED    NOT NULL DEFAULT 0,
  active_passenger_id BIGINT UNSIGNED
    GENERATED ALWAYS AS (IF(status < 60, passenger_id, NULL)) STORED,
  dispatch_started_at DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
    COMMENT '本轮匹配起点, 决定半径与60秒超时',
  created_at        DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  accepted_at       DATETIME(3)     NULL,
  updated_at        DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (order_id),
  UNIQUE KEY uk_passenger_request (passenger_id, request_id),
  UNIQUE KEY uk_active_passenger (active_passenger_id),
  KEY idx_dispatch (city_id, region_id, status, created_at),
  KEY idx_passenger (passenger_id, created_at),
  KEY idx_driver (driver_id, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单';

CREATE TABLE driver_runtime (
  driver_id         BIGINT UNSIGNED NOT NULL,
  city_id           INT UNSIGNED    NOT NULL COMMENT '营运城市',
  car_type          TINYINT         NOT NULL,
  state             TINYINT         NOT NULL DEFAULT 0 COMMENT '0离线 1空闲 2待应答 3服务中',
  current_order_id  BIGINT UNSIGNED NULL,
  current_offer_id  BIGINT UNSIGNED NULL,
  version           BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '同步Redis状态提示时防乱序',
  updated_at        DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (driver_id),
  KEY idx_city_state (city_id, state, updated_at)
) ENGINE=InnoDB COMMENT='司机占用状态(权威)';

CREATE TABLE dispatch_offer (
  offer_id          BIGINT UNSIGNED NOT NULL,
  order_id          BIGINT UNSIGNED NOT NULL,
  driver_id         BIGINT UNSIGNED NOT NULL,
  batch_id          BIGINT UNSIGNED NOT NULL,
  status            TINYINT         NOT NULL DEFAULT 0
    COMMENT '0待应答 1接受 2拒绝 3超时 4撤销 5接单后取消',
  eta_seconds       INT UNSIGNED    NOT NULL,
  distance_m        INT UNSIGNED    NOT NULL,
  score             DECIMAL(12,4)   NOT NULL COMMENT '匹配得分, 用于回放分析',
  expire_at         DATETIME(3)     NOT NULL,
  responded_at      DATETIME(3)     NULL,
  created_at        DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  pending_driver_id BIGINT UNSIGNED GENERATED ALWAYS AS (IF(status = 0, driver_id, NULL)) STORED,
  pending_order_id  BIGINT UNSIGNED GENERATED ALWAYS AS (IF(status = 0, order_id, NULL)) STORED,
  accepted_order_id BIGINT UNSIGNED GENERATED ALWAYS AS (IF(status = 1, order_id, NULL)) STORED,
  PRIMARY KEY (offer_id),
  UNIQUE KEY uk_order_driver (order_id, driver_id),
  UNIQUE KEY uk_pending_driver (pending_driver_id),
  UNIQUE KEY uk_pending_order (pending_order_id),
  UNIQUE KEY uk_accepted_order (accepted_order_id),
  KEY idx_status_expire (status, expire_at),
  KEY idx_driver (driver_id, created_at)
) ENGINE=InnoDB COMMENT='派单记录';

CREATE TABLE outbox_event (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  event_type    VARCHAR(32)     NOT NULL COMMENT 'ORDER_CREATED/OFFER_PUSH/DRIVER_STATE',
  biz_id        BIGINT UNSIGNED NOT NULL,
  payload       JSON            NOT NULL,
  status        TINYINT         NOT NULL DEFAULT 0 COMMENT '0待发送 1已发送',
  retry_count   INT UNSIGNED    NOT NULL DEFAULT 0,
  next_retry_at DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  created_at    DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  KEY idx_send (status, next_retry_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='本地消息表';

-- ClickHouse: 轨迹明细 (ReplacingMergeTree 对重传做最终去重)
CREATE TABLE driver_trajectory (
  city_id    UInt32,
  driver_id  UInt64,
  order_id   UInt64 DEFAULT 0,
  gps_time   DateTime64(3),
  recv_time  DateTime64(3),
  lat        Float64,
  lng        Float64,
  speed_kmh  Float32,
  heading    UInt16
) ENGINE = ReplacingMergeTree
PARTITION BY toYYYYMMDD(gps_time)
ORDER BY (driver_id, gps_time)
TTL toDateTime(gps_time) + INTERVAL 30 DAY;
```

三个生成列唯一索引是数据库层最后一道防线：同一司机最多一条待应答、同一订单最多一条待应答、同一订单最多一条接受记录（MySQL 唯一索引允许多个 NULL）。

## 四、核心流程

### 1. 位置上报与索引维护

接口（长连接消息）：`location.report {driverId, gpsTs, lat, lng, speed, heading, orderId}`

1. Location Service 丢弃时间戳异常和明显漂移（推算速度超过 180km/h）的点。
2. 用 H3 分辨率 8 计算格子（平均边长约 0.53km，面积约 0.74 平方公里）。
3. 对单个司机 key 执行 Lua：拒绝乱序点，更新位置并返回旧格子。

```
-- KEYS[1]=drv:<driverId>  ARGV: gpsTs, cell, lat, lng
local ts = redis.call('HGET', KEYS[1], 'ts')
if ts and tonumber(ts) >= tonumber(ARGV[1]) then return {0, ''} end
local old = redis.call('HGET', KEYS[1], 'cell')
redis.call('HSET', KEYS[1], 'ts', ARGV[1], 'cell', ARGV[2], 'lat', ARGV[3], 'lng', ARGV[4])
redis.call('PEXPIRE', KEYS[1], 600000)
return {1, old or ''}
```

4. `ZADD geo:<city>:<cell> <服务端时间ms> <driverId>`；若跨格再对旧格子 ZREM。key 名里不能写花括号包住 city，否则 hash tag 会让整城落到一个槽。
5. 跨 key 操作不做原子保证：读侧用 score 过滤 15 秒内无上报的成员，并核对司机 hash 里的 cell 是否一致；写侧以 1% 概率执行 ZREMRANGEBYSCORE 清理 60 秒前成员，格子 key 设 120 秒过期并在写入时续期。
6. 异步写 Kafka。行程中的轨迹用于计费，生产端 acks=all，司机端断网时本地缓存并补传。

### 2. 附近司机召回

- 从中心格子逐圈向外查：`ZRANGE geo:<city>:<cell> +inf <now-15000> BYSCORE REV LIMIT 0 100`，按节点 pipeline。
- 分辨率 8 下覆盖 3km / 5km / 8km 约需 k = 4 / 7 / 11 圈（61 / 169 / 397 个格子）。凑够 30 个候选后再多查一圈即停，稠密区域很早结束。
- 批量读司机 hash，过滤格子不一致、非空闲、车型不符、超出实际半径者。状态提示缺失时保留，交给数据库判断。
- 附近车辆展示只查 k=2（19 格），Nearby Service 按分辨率 5 父格子一致性哈希路由，格子结果本地缓存 2 秒并做请求合并，返回最多 10 辆且坐标做模糊处理。

### 3. 下单

`POST /v1/orders {requestId, pickup, dropoff, carType}`

同一事务写 ride_order（status=10）和 outbox。重复 requestId 返回原订单；已有进行中订单被 uk_active_passenger 拒绝（跨城跨分片的情况由订单服务按乘客维度额外校验）。Outbox 投递到 dispatch_request。

### 4. 批量匹配（每区域每 1.5 秒）

1. 引擎实例通过 etcd 租约认领区域，订阅对应分区放入内存待匹配池；每 5 秒扫库中 status=10 的订单兜底，因此消费位点丢失不丢单。
2. 按本轮已匹配时长（自 dispatch_started_at 起）定半径：0~20s 为 3km，20~40s 为 5km，40~60s 为 8km；超过 60s 且订单仍为 10 时置 91。
3. 每单取直线距离最近的 30 名候选，排除 dispatch_offer 中派过该单的司机；前 10 名请求 ETA。
4. 建二分图，边权 = BASE - ETA + a x 已等待时间 + b x 司机服务分。BASE 取足够大以优先提高匹配数。按连通分量用 KM 求最大权匹配；分量超过 500 个节点时退化为按边权排序贪心。
5. 对每个匹配对：先 `SET dlock:<driverId> <offerId> NX PX 3000` 做廉价预过滤，再执行事务：

```
BEGIN;
UPDATE ride_order SET status=20, current_offer_id=:offer, version=version+1
 WHERE order_id=:order AND status=10 AND version=:ver;
UPDATE driver_runtime SET state=2, current_order_id=:order,
       current_offer_id=:offer, version=version+1
 WHERE driver_id=:driver AND city_id=:city AND state=1;
INSERT INTO dispatch_offer(... status=0, expire_at=NOW(3)+INTERVAL 15 SECOND);
INSERT INTO outbox_event(... 'OFFER_PUSH'), (... 'DRIVER_STATE');
COMMIT;
```

任一 UPDATE 影响行数不为 1 或唯一键冲突则整体回滚，订单回池等下一批。提交后按 version 条件更新 Redis 状态提示（司机 hash 中的 st、sv 字段），并用比较后删除的 Lua 释放 dlock。司机 CAS 失败时顺手回写正确状态，避免反复选中同一人。相邻区域引擎抢到同一边界司机时，由司机行 CAS 决出唯一胜者。

### 5. 接单

`POST /v1/offers/{offerId}/accept`

```
BEGIN;
UPDATE ride_order SET status=30, driver_id=:driver, accepted_at=NOW(3), version=version+1
 WHERE order_id=:order AND status=20 AND current_offer_id=:offer;
UPDATE dispatch_offer SET status=1, responded_at=NOW(3)
 WHERE offer_id=:offer AND driver_id=:driver AND status=0 AND expire_at>=NOW(3);
UPDATE driver_runtime SET state=3, version=version+1
 WHERE driver_id=:driver AND state=2 AND current_offer_id=:offer;
INSERT INTO outbox_event(... 'DRIVER_STATE');
COMMIT;
```

三条都影响 1 行才提交，否则回滚并返回"订单已失效"。若该 offer 已是接受状态，按幂等返回成功。过期判断一律用数据库时间；司机端倒计时显示 13 秒留出网络余量。

### 6. 拒单、超时、取消

- 拒单与超时：事务内先把订单 20 改回 10（条件含 current_offer_id），再把 offer 置 2 或 3，最后司机 2 改回 1，提交后订单重新进入待匹配池。
- 超时由延迟队列触发，另有每秒一次的扫描器处理过期超过 2 秒仍为 0 的记录。
- 接单与超时、乘客取消的竞争：所有事务都先更新订单行，行锁串行化，后到者 CAS 失败。
- 乘客取消：订单置 90，待应答 offer 置 4（已接单则置 5），司机释放。接单后司机取消：offer 置 5，订单回 10、清空 driver_id 并重置 dispatch_started_at 后重新派。
- 司机下线：空闲直接置 0；待应答按拒单处理后下线；服务中不允许下线。

## 五、方案取舍

### 地理索引

| 方案 | 优点 | 缺点 |
|---|---|---|
| H3 网格 + Redis ZSET（采用） | 按格子打散到集群；邻居中心距离一致；自带按时间过滤 | 需自行处理跨格移动与过期；一次召回扇出多个 key |
| 每城一个 Redis GEO key | 实现简单，GEOSEARCH 现成 | 大城市成为热 key，单分片 CPU 封顶；成员无单独过期 |
| 引擎内存网格（消费 Kafka） | 延迟最低，无网络扇出 | 有状态，重启需回放；区域边界和扩缩容复杂。适合作超大城市演进或降级 |
| MySQL / PostGIS 空间索引 | 查询表达力强，持久化 | 难以承受 25 万/s 更新 |

### 派单模式

| 方案 | 优点 | 缺点 |
|---|---|---|
| 批量二分图匹配（采用） | 一批内整体接驾时间和匹配率更优 | 增加最多 1.5 秒等待；实现与调参复杂 |
| 来单即派最近司机 | 延迟低，逻辑简单 | 局部最优，后来订单可能无车可派 |
| 广播抢单 | 服务端简单，司机有选择权 | 推送放大、并发争抢、远车接单、网络差的司机吃亏 |

### 防重复派单

| 方案 | 优点 | 缺点 |
|---|---|---|
| MySQL 条件更新 + 唯一索引，Redis 锁仅预过滤（采用） | 切主、过期、双引擎脑裂下仍正确 | 每次派单走一次数据库事务 |
| 仅 Redis 分布式锁 | 快 | 异步复制切主可能丢锁；进程停顿导致锁过期后仍写入 |
| 每城单线程内存串行分配 | 无锁，逻辑直观 | 单点吞吐上限；故障恢复需重建状态，脑裂仍需存储层校验 |

### 分片键

| 方案 | 优点 | 缺点 |
|---|---|---|
| 按 city_id（采用） | 订单与司机同库，本地事务；城市天然隔离 | 分片不均，需城市到分片的映射表，大城市独占 |
| 按 order_id 哈希 | 分布均匀 | 订单与司机跨库，需要分布式事务或 TCC |

## 六、容灾、监控与扩展

### 容灾

- Redis 节点切主或清空：位置是软状态，1~2 个上报周期（4~8 秒）自动重建，不需要持久化；重复派单由数据库拦截。
- Redis Geo 大面积不可用：引擎切换为消费 driver_location 构建的内存影子索引（超大城市常态预热）；附近车辆展示直接降级隐藏。
- 引擎实例宕机：租约（约 5 秒 TTL）过期后他人接管，从数据库加载 status=10 订单；短暂双主只会增加 CAS 冲突。
- Kafka 故障：outbox 积压，引擎靠扫库继续派单（扫描间隔临时缩到 1 秒）。
- MySQL 主库故障：半同步（AFTER_SYNC，超时调大避免静默退化为异步）或 MGR；切换期间该分片城市暂停派单，其他城市不受影响。
- ETA 超时（200ms）：熔断，改用直线距离 x 1.4 / 当前区域平均车速。
- 推送丢失：司机端心跳携带 current_offer_id，不一致时下发；重连后调用 GET /v1/driver/current-offer。
- 过载保护：按序降级附近车辆刷新频率、非空闲司机上报频率放宽到 8 秒、缩小候选数；派单与接单链路最后降级。
- 机场、火车站：地理围栏内改用独立 FIFO 排队队列派单，避免单格子堆积数千司机和插队争议。

### 监控与告警

- 业务：下单到派单 P99（> 3s 告警）、匹配成功率、接单率、超时率、接驾 ETA P50/P90、60 秒无车率。
- 一致性巡检（每分钟）：司机 state=2 且无有效 offer 超过 30 秒；订单 status=20 无待应答记录；司机 state=3 但订单已结束。预期恒为 0，发现即按订单状态修复并告警。
- 索引质量：司机 CAS 冲突率（> 5% 说明状态提示滞后）、幽灵司机过滤比例、位置端到端延迟与丢弃率。
- 系统：批次耗时与窗口之比（> 0.8 需拆区）、区域待匹配积压、outbox 最老事件年龄、Redis 单节点 CPU 与热 key、DB 行锁等待。

### 扩展

- 新增城市：映射到现有或新分片；城市迁移采用双写校验后切路由，低峰执行。
- 大城市：区域按订单密度动态拆分与合并，换主依赖租约，安全性不依赖路由一致。
- 拼车与连环单：state 换为座位容量与订单列表，CAS 条件改为剩余容量；current_order_id 与 uk_pending_driver 隐含的单订单假设要一起调整。
- 派单策略：边权可接入接单概率模型；用 dispatch_offer 与轨迹做离线回放和按区域时间片的 A/B 实验。
