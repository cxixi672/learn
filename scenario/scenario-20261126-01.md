# scenario-20261126-01：电商商品搜索：MySQL 到 Elasticsearch 准实时同步、零停机重建索引与搜索降级

## 一、题目

**业务背景**：电商平台商品搜索原先靠定时任务把 MySQL 同步到单个 ES 索引，大促时改价延迟十几分钟、违规商品下架后仍能搜到、改分词器要停服重建。现要求重新设计。

**需求约束**

- 数据量：可检索 SPU 约 6000 万（含近期下架），平均每个 SPU 6 个 SKU，100 万店铺。
- 读：日搜索 6 亿次（均值约 7000 QPS），大促峰值 3 万 QPS；端到端 P99 < 200ms，ES 查询 P99 < 100ms。
- 写：日常商品变更 2000 万次/天；大促改价与库存变更峰值 5 万条/s。
- 一致性：下架/违规商品 5 秒内搜不到；标题、价格变更 P99 5 秒内可检索；列表展示价 P99 3 秒内更新（成交价以下单时 DB 为准）；销量等排序特征允许 10 分钟延迟。
- 功能：关键词、类目、品牌、价格区间、属性过滤，分面聚合，综合/销量/价格排序，最多翻 100 页。
- 运维：mapping 或分词器升级时零停机、可回滚，全量重建小于 6 小时；单个 ES 集群故障时搜索仍可用（允许降级）。

## 二、整体架构

```
[写链路]

  Product / Stock / Ops services
        |  write
        v
  MySQL (sharded by spu_id)
        |  binlog (ROW, FULL image)
        v
  Canal / Flink CDC  -->  Change Router            提取 spu_id 并分级
        |
        +--> product_change_urgent                 上下架、审核状态
        +--> product_change                        标题、价格、有货/无货翻转
        +--> product_change_low                    销量、评分
        |
        v
  Index Builder                                    合并去重 -> 分配版本号 -> 回查主库 -> 组装宽文档
        |
        +--> Redis  spu:snap:{spuId}               商品快照，按版本号覆盖
        |
        +--> Kafka  product_doc  (key = spu_id)
                 |
                 +--> ES Writer A --> ES Cluster A (product_v7, product_v8)
                 +--> ES Writer B --> ES Cluster B (product_v7, product_v8)
                        bulk, version_type = external

[全量重建]
  Reindex Scheduler -> product_full -> Rebuild Builder -> product_doc_full -> 目标集群的新索引

[紧急封禁]
  Risk Platform -> spu_block + Kafka spu_block_event -> 每个 Search 节点的本地黑名单

[读链路]

  App / Web --> API Gateway --> Search Service
                                  |  1. query rewrite          归一化、纠错、类目预测
                                  |  2. Redis recall cache     未命中时 singleflight 回源
                                  |  3. ES recall top 200      按用户哈希路由到集群 A 或 B
                                  |  4. Ranking Service        个性化精排
                                  |  5. block filter + hydrate  黑名单过滤，用快照补价格与状态
                                  v
                               result
```

**容量估算（单分片查询 CPU 4ms 为假设值，上线前必须压测校准）**

- 主分片数据约 6000 万 x 3KB = 180GB，12 个主分片（每片约 15GB）；nested 使 Lucene 文档数约 4.2 亿。
- 两个独立集群，各 3 个专用 master + 24 个数据节点（32C / 128G / SSD，堆内存不超过 31G），1 副本，每节点 1 个分片。
- 缓存命中率按 40%，ES 查询 1.8 万 QPS，每集群 9000 QPS x 12 分片 x 4ms / 24 节点 = 每节点约 18 核（56%），余量给写入与段合并。
- 单集群故障时负载翻倍到 36 核，超过上限，必须降级：关闭分面、延长缓存使命中率升到 65%，此时每节点约 21 核（66%）。

## 四、核心流程

### 1. 增量同步

1. Canal 订阅 binlog，Change Router 只提取 spu_id 并分级投递。库存变更仅在 available 跨越 0（有货与无货翻转）时投递，过滤掉绝大部分库存流量（依赖 binlog 前镜像）。
2. Builder 以 500ms 或 500 条为窗口按 spu_id 去重。大促 5 万条/s 的 SKU 级变更按 SPU 合并后预计 1 万到 1.5 万次构建/s。三个优先级用独立消费组和线程池，低优积压不影响下架。
3. 每批先在事务内分配版本号并提交，再从主库（库存走库存服务主库接口）读最新数据组装整篇文档。消息只是“某 SPU 脏了”的信号，不携带数据，因此天然幂等、可重放、不怕乱序。
4. 为什么能保证最终正确：任一变更 C 提交后触发的构建拿到版本 v；版本大于 v 的构建，分配版本晚于它，而读数据又晚于自己的版本分配，所以一定在 C 提交之后读取。因此最终胜出的文档必然包含 C。前提是回查读主库，且先分配版本后读数据。
5. Builder 先用 Lua 按版本写 Redis 快照，再投递 product_doc，两者都成功后提交位点。
6. ES Writer 用 bulk 写入，version_type=external。409 版本冲突视为成功（已有更新版本）；429 退避重试并暂停拉取；400 类错误写 index_fail_log 并告警。
7. 删除不做物理删除，写 status=下架/删除 的墓碑文档。原因：ES 删除后版本信息默认只保留 60 秒（index.gc_deletes），迟到的旧消息会让商品“复活”。墓碑保留 7 天（大于 Kafka 3 天保留期）后由定时任务清理。

快照写入脚本：

```lua
-- KEYS[1]=spu:snap:{spuId}  ARGV: version, status, minPrice, hasStock
local cur = tonumber(redis.call('HGET', KEYS[1], 'ver') or '0')
if tonumber(ARGV[1]) <= cur then return 0 end
redis.call('HSET', KEYS[1], 'ver', ARGV[1], 'status', ARGV[2],
           'min_price', ARGV[3], 'has_stock', ARGV[4])
return 1
```

时延预算：CDC 0.5s + 合并 0.5s + 构建 0.3s + 写入排队 0.7s + refresh 1s，约 3s，小于 5s。

### 2. 下架与违规的三道防线

1. ES 文档经 urgent 通道更新 status，查询固定过滤 status=1。
2. 返回前用 Redis 快照校验状态并补齐价格，即使召回缓存是旧的也不会漏出已下架商品。
3. 风控封禁接口同步写 spu_block 并广播事件，Search 节点本地黑名单即时过滤，每 60 秒全量重载兜底。该路径不依赖 CDC 与 ES。

过滤后某页可能少几条，业务上可接受，不做跨页补齐。

### 3. 查询接口

`GET /api/v1/search?q=&category_id=&brand_ids=&price_min=&price_max=&attrs=&sort=&page=&page_size=20`，返回 items、total（超过 1 万显示 1 万+）、degraded 标记。

```json
POST product_read/_search?preference=u_8f3a
{
  "size": 200, "_source": false, "track_total_hits": 10000, "timeout": "80ms",
  "docvalue_fields": ["min_price", "sales_30d", "quality_score"],
  "query": { "function_score": {
    "query": { "bool": {
      "must":   [ { "multi_match": { "query": "红色连衣裙",
                    "fields": ["title^3", "title.uni^0.2"], "minimum_should_match": "75%" } } ],
      "filter": [ { "term": { "status": 1 } },
                  { "nested": { "path": "skus", "query": { "bool": { "filter": [
                      { "term":  { "skus.sale_kv": "尺码:M" } },
                      { "range": { "skus.price": { "gte": 10000, "lte": 30000 } } },
                      { "term":  { "skus.in_stock": true } } ] } } } } ] } },
    "functions": [
      { "weight": 1 },
      { "field_value_factor": { "field": "sales_30d", "modifier": "log1p", "missing": 0 }, "weight": 0.2 },
      { "filter": { "term": { "has_stock": true } }, "weight": 0.5 } ],
    "score_mode": "sum", "boost_mode": "multiply" } },
  "sort": [ "_score", { "spu_id": "asc" } ]
}
```

- 过滤条件放 filter（不算分、可缓存）；销售属性与 SKU 价格组合过滤走 nested，保证命中同一个 SKU；普通属性过滤和分面走扁平的 attr_kv。
- 召回缓存存 Top200 的 ID 与特征，key 为归一化查询+过滤+排序的哈希，TTL 30 到 60 秒随机。个性化精排结果按会话缓存 10 分钟，保证翻页不重复。
- 第 1 到 10 页从 Top200 切片；第 11 到 100 页走 from/size（from 从 200 起，最大 2000，低于默认 10000 上限）；价格与销量排序不做精排。超过 100 页拒绝；内部导出用 PIT + search_after。
- 分面单独发 size=0 请求，缓存 5 分钟，可独立降级。

### 4. 零停机重建索引（逐集群灰度）

1. 建 product_v8：加载期 number_of_replicas=0、refresh_interval=-1；在 search_index_meta 登记 state=构建中、write_enabled=1。
2. 开启双写：该集群 Writer 对 v7、v8 写同一文档同一版本。必须等所有 Writer 实例心跳确认已加载新 config_version，才能开始全量扫描。v8 写失败只记 fail_log，不阻塞 v7。
3. Reindex 调度器按库分片和 ID 区间认领任务（租约 + checkpoint 可断点续跑），投递 spu_id 到 product_full，复用同一套构建逻辑与版本序列，所以全量永远不会覆盖更新的实时数据。目标 1 万条/s，约 1.7 小时，按主库负载限速。
4. 加载完成后恢复副本与 refresh_interval=1s，等集群 green 并预热。
5. 校验：文档数、按 ID 抽样比对字段、回放线上查询对比 Top20 重合度和延迟、零结果率。
6. 原子切别名，再灰度另一个集群：

```json
POST _aliases
{ "actions": [
  { "remove": { "index": "product_v7", "alias": "product_read" } },
  { "add":    { "index": "product_v8", "alias": "product_read" } } ] }
```

7. v7 继续双写 24 到 72 小时，回滚只需把别名切回；确认无误后停写并删除。

## 五、方案取舍

**数据同步方式**

| 方案 | 优点 | 缺点 |
|---|---|---|
| CDC 发脏 ID + 回查构建整文档（本方案） | 业务零侵入；多表聚合简单；幂等可重放；全量与增量共用一套逻辑 | 回查给主库增加读压力，需批量与合并；链路组件多 |
| 业务代码同步双写 DB 和 ES | 链路最短，延迟低 | 无法保证原子性，ES 抖动拖垮写接口；入口多易漏写 |
| Flink CDC 多表流式 Join 写 ES | 不回查 DB，吞吐高 | 状态巨大，乱序与回撤处理复杂，改字段需重建状态 |
| 定时轮询 updated_at | 实现最简单 | 分钟级延迟；物理删除丢失；长事务提交晚于扫描水位会漏数据 |
| 只用 MySQL LIKE 或全文索引 | 无同步问题，强一致 | 分词、相关性、分面能力弱，扛不住该量级 |

**乱序控制方式**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 版本表序号 + external version（本方案） | 跨表单调；全量与增量并发安全 | 每次构建多一次写库 |
| 用 updated_at 毫秒时间戳做版本 | 无额外写入 | 多表取最大值在删行时会倒退；时钟回拨和同毫秒变更会丢更新 |
| 只依赖 Kafka 分区顺序 | 无需版本 | rebalance、重试、全量并发时旧数据会覆盖新数据 |
| ES 局部更新 _update | 写入数据量小 | 不支持 external version，多写入方难以定序；底层仍是整文档重写 |

**文档模型**

| 方案 | 优点 | 缺点 |
|---|---|---|
| SPU 文档 + 扁平 attr_kv + nested SKU（本方案） | 结果天然按商品聚合；组合过滤准确 | 任一 SKU 变化重写整个 nested 块；nested 查询有开销 |
| SKU 级文档 + collapse 折叠 | 单次更新小 | 总数与聚合按 SKU 计算，需额外去重，精度和性能差 |
| SPU 纯扁平数组 | 查询最快 | 会跨 SKU 误匹配（红色 S 码和蓝色 M 码命中“红色 M 码”） |

**高可用部署**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 双独立集群各自消费（本方案） | 故障域隔离；可逐集群升级和重建 | 成本高；两边短时间结果可能略有差异，需按用户固定路由 |
| 单集群加副本跨可用区 | 成本低、运维简单 | master、mapping、版本升级故障影响全部流量 |
| ES 跨集群复制 CCR | 无需自建双写 | 需要付费订阅；从集群 mapping 跟随主集群，难以独立重建 |

## 六、容灾、监控与扩展

**容灾与降级**

- 分级开关：L1 关闭个性化精排（超时 50ms 也自动跳过）；L2 关闭分面并把缓存 TTL 提到 5 分钟、限制翻页到 10 页；L3 只返回缓存与预计算热词结果，其余返回类目热销榜并限流。
- 单集群故障：健康检查与错误率触发，把流量切到另一集群并自动进入 L2，超出容量部分按用户限流。
- Kafka 或 CDC 故障：位点保留后追数（binlog 至少保留 3 天）；期间下架靠封禁通道直接生效，必要时运营把批量下架同时写入 spu_block。
- Redis 故障：召回缓存失效时 ES 压力上升，直接进入 L2；快照不可读时信任 ES 数据，黑名单在本地内存不受影响。
- 版本表主从切换丢数据会使版本倒退、写入全部 409：版本库用半同步复制；发生切换后把受影响分片的 build_version 整体加一个大偏移量，再按时间窗口重投 spu_id。
- 防慢查询打垮集群：禁止前缀通配和脚本排序，限制关键词长度与 terms 数量，Search 服务按查询类型做线程池隔离与超时。

**监控与对账**

- 新鲜度探针：每 10 秒改一次测试 SPU（查询侧对普通用户过滤），测量到两个集群可检索的端到端时延，P99 超过 5 秒告警。
- 链路：CDC 延迟、各 topic 积压（urgent 超过 2 秒告警）、构建 TPS、bulk 拒绝数、409 比例、fail_log 积压。
- 查询：P99、超时与部分结果比例、线程池 rejected、堆与 GC、缓存命中率、零结果率、降级次数。
- 对账：每小时按 updated_at 回扫近 2 小时变更，与 ES 的 source_updated_at 比对，不一致就重投 spu_id；每天全量核对下架与封禁商品不可检索。

**扩展性与易踩的坑**

- QPS 增长：加数据节点和副本；数据量增长：走重建流程扩主分片。店铺内搜索量大时单独建按 shop_id 路由的索引，注意大店铺倾斜。
- IK 的 ik_smart 分词结果不保证是 ik_max_word 的子集，可能搜不到，所以加单字子字段低权重兜底并监控零结果词。
- 同义词用搜索期 updateable 过滤器，调用 _reload_search_analyzers 热更新（同时清请求缓存）；索引期词典变化需要重建索引。
