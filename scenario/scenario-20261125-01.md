# scenario-20261125-01：开放平台 API 网关多租户分布式限流与配额：令牌桶、本地预取租约、降级与动态规则

## 一、题目

- 日均调用 80 亿次，网关集群峰值 120 万 QPS，30 台网关节点；开放平台有 10 万租户（ISV），约 2000 个对外 API。
- 限流维度：租户级（总 QPS）、租户+API 级、IP 级、全局保护级；另有按日/按月的调用配额（付费套餐，超额即拒绝或计费）。
- 限流判定增加的网关延迟 P99 < 1ms（均值 < 0.3ms）；限流误差可容忍 ±10%，但配额计费误差要求 < 0.1%，不能少记也不能重复记。
- 某大租户突发流量不能拖垮其他租户（隔离）；Redis 或配置中心故障时网关不能全部拒绝或全部放行（要有可预期的降级策略）。
- 规则由运营后台动态修改，30 秒内全网生效；被限流请求必须返回 429 + Retry-After，并可按租户查询被拒绝次数用于运营与客诉。

## 二、整体架构

```
  客户端(ISV)
     │ HTTPS 请求 (appKey + 签名)
     v
  [LB / 接入层] ──> [API 网关集群 x30]
                        │
        ┌───────────────┼──────────────────────────────┐
        │ ①鉴权取租户   │ ②本地规则缓存(Caffeine)       │
        │               │     规则版本号 / 套餐 / 阈值   │
        │               v                               │
        │   [一级: 本地令牌桶 (节点内, 纳秒级)]          │
        │     节点份额 = 租户阈值 x 权重 (超限直接 429)   │
        │               │ 本地桶空 -> 向 Redis 申请租约  │
        │               v                               │
        │   [二级: Redis Cluster 全局令牌桶 (Lua)]       │
        │     key = rl:{tenant}:{api}  一次领取 N 个令牌  │
        │               │                               │
        │               v                               │
        │   [三级: 配额计数 (本地累加, 批量 INCRBY)]      │
        │     quota:{tenant}:{yyyyMMdd}                 │
        └───────────────┬───────────────────────────────┘
                        │ 放行 -> 转发后端服务
                        v
                  [后端业务服务]

  规则下发:  运营后台 ──> [MySQL 规则表] ──> [配置中心/Nacos] ──推送──> 各网关节点本地缓存
                                         └─> binlog 订阅 -> 预热 Redis 配置
  配额落库:  网关 ──异步 INCRBY──> Redis ──定时(1min)刷盘──> MySQL quota_usage (对账/计费)
  拒绝统计:  网关 ──> 本地聚合(10s) ──> Kafka reject_topic ──> Flink ──> ClickHouse (报表/告警)
  监控:      Prometheus 采集 QPS/拒绝率/Redis RT/降级次数 ──> Grafana + 告警
```

## 三、关键表设计与脚本

```sql
-- 1. 限流规则表（规则维度可叠加，取最严格者）
CREATE TABLE rate_limit_rule (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  rule_code    VARCHAR(64)  NOT NULL COMMENT '规则唯一编码',
  scope_type   TINYINT      NOT NULL COMMENT '1全局 2租户 3租户+API 4IP',
  tenant_id    BIGINT       NOT NULL DEFAULT 0 COMMENT '0表示所有租户默认规则',
  api_code     VARCHAR(128) NOT NULL DEFAULT '*' COMMENT '*表示所有API',
  algo         TINYINT      NOT NULL DEFAULT 1 COMMENT '1令牌桶 2滑动窗口',
  rate_per_sec INT          NOT NULL COMMENT '稳定速率 QPS',
  burst        INT          NOT NULL COMMENT '桶容量(突发上限)',
  priority     INT          NOT NULL DEFAULT 0 COMMENT '数值大者优先匹配',
  status       TINYINT      NOT NULL DEFAULT 1 COMMENT '1启用 0停用',
  version      BIGINT       NOT NULL DEFAULT 1 COMMENT '乐观锁/规则版本',
  updated_by   VARCHAR(64)  NOT NULL,
  created_at   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_rule_code (rule_code),
  KEY idx_tenant_api (tenant_id, api_code, status),
  KEY idx_updated_at (updated_at)
) ENGINE=InnoDB COMMENT='限流规则';

-- 2. 租户套餐与配额
CREATE TABLE tenant_quota (
  tenant_id     BIGINT UNSIGNED NOT NULL,
  plan_code     VARCHAR(32) NOT NULL COMMENT '套餐: free/pro/enterprise',
  daily_quota   BIGINT      NOT NULL COMMENT '日调用上限, -1不限',
  monthly_quota BIGINT      NOT NULL COMMENT '月调用上限, -1不限',
  over_policy   TINYINT     NOT NULL DEFAULT 1 COMMENT '1超额拒绝 2超额放行并计费',
  effective_at  DATETIME    NOT NULL,
  expire_at     DATETIME    NOT NULL,
  updated_at    DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (tenant_id),
  KEY idx_expire (expire_at)
) ENGINE=InnoDB COMMENT='租户配额';

-- 3. 配额用量（Redis 定时刷盘，按日分区，用于计费与对账）
CREATE TABLE quota_usage (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  tenant_id   BIGINT   NOT NULL,
  api_code    VARCHAR(128) NOT NULL,
  stat_date   DATE     NOT NULL,
  used_count  BIGINT   NOT NULL DEFAULT 0 COMMENT '放行次数',
  reject_count BIGINT  NOT NULL DEFAULT 0 COMMENT '被限流次数',
  flush_seq   BIGINT   NOT NULL DEFAULT 0 COMMENT '刷盘序号, 幂等用',
  updated_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_tenant_api_date (tenant_id, api_code, stat_date),
  KEY idx_date (stat_date)
) ENGINE=InnoDB COMMENT='配额用量';

-- 4. 规则变更审计
CREATE TABLE rate_limit_rule_audit (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  rule_id    BIGINT   NOT NULL,
  op_type    TINYINT  NOT NULL COMMENT '1新增 2修改 3停用',
  before_val JSON NULL,
  after_val  JSON NULL,
  operator   VARCHAR(64) NOT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_rule (rule_id, created_at)
) ENGINE=InnoDB COMMENT='规则变更审计';

-- Redis 全局令牌桶 Lua（原子：补充令牌 + 扣减，一次可领取 need 个作为本地租约）
-- KEYS[1]=rl:{tenant}:{api}  ARGV: rate, burst, now_ms, need
local d = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(d[1]) or tonumber(ARGV[2])
local ts     = tonumber(d[2]) or tonumber(ARGV[3])
local delta  = math.max(0, tonumber(ARGV[3]) - ts)
tokens = math.min(tonumber(ARGV[2]), tokens + delta * tonumber(ARGV[1]) / 1000)
local need = tonumber(ARGV[4]); local got = 0
if tokens >= need then got = need elseif tokens >= 1 then got = math.floor(tokens) end
tokens = tokens - got
redis.call('HMSET', KEYS[1], 'tokens', tokens, 'ts', ARGV[3])
redis.call('PEXPIRE', KEYS[1], 60000)
return got
```

## 四、核心流程

1. **请求判定主流程**：网关收到请求先鉴权得到 tenantId 和 apiCode，从本地规则缓存匹配出所有生效规则（租户级、租户+API 级、IP 级、全局级），逐级判定，任一不通过即返回 429。判定顺序为：全局保护 → IP → 租户 → 租户+API → 配额，开销小、拦截面大的放前面。
2. **本地租约机制（核心优化）**：如果每个请求都访问 Redis，120 万 QPS 会直接压垮集群。因此每个网关节点为每个活跃的 租户+API 维护一个本地令牌桶。本地桶余额不足时，调用 Redis Lua 一次领取 N 个令牌（N = 该租户近 1 秒本节点请求量的 1.2 倍，上下限 10~1000）作为租约，之后在本地消耗。这样 Redis 的调用量从请求级降到 租约级，实测可降低 95% 以上。令牌租约有 200ms 的有效期，过期作废，避免某节点囤积令牌。
3. **全局速率保证**：Redis 中的全局桶以租户阈值为速率产生令牌，所有节点领取的令牌总和不会超过阈值，因此全局总量是准确的；误差只来自租约在节点内的滞留（≤200ms × 速率），在 ±10% 容忍范围内。对阈值很小的租户（如 QPS < 30），关闭租约机制，直接请求级访问 Redis，保证精度。
4. **配额计数**：放行请求时在本地 LongAdder 中累加，每 1 秒批量 INCRBY 到 Redis（key 为 quota:{tenant}:{yyyyMMdd}，带 48 小时过期），返回的最新总量同时用于判断是否超额，并缓存到本地。每分钟由刷盘任务把 Redis 增量写入 MySQL quota_usage（用 flush_seq 保证幂等，重复刷盘不会重复累加）。配额接近 90% 时发告警通知租户，超额后按 over_policy 拒绝或放行计费。因为有 1 秒的批量延迟，最多超额 1 秒的请求量，业务可接受。
5. **动态规则下发**：运营后台修改规则时写 MySQL 并写审计表，同时发布到配置中心（Nacos），网关监听变更后更新本地缓存；每 30 秒再做一次基于 version 的全量拉取兜底，保证即使推送丢失也能在 30 秒内收敛。规则变更不重置 Redis 令牌桶，新阈值在下一次 Lua 调用中生效。
6. **被拒绝请求处理**：返回 HTTP 429，响应头带 Retry-After（按令牌补充速度估算）与 X-RateLimit-Limit/Remaining。网关本地每 10 秒聚合 reject 计数，发送到 Kafka，再由 Flink 汇总入 ClickHouse，用于租户维度的报表、客诉查询，以及异常租户（短时间大量 429）的告警。
7. **故障降级**：Redis 调用超时（>5ms）或异常时，按『熔断 + 本地兜底』处理：连续失败 5 次触发熔断 10 秒，期间使用本地令牌桶，阈值为 租户阈值 ÷ 网关节点数 × 1.5 的宽松份额，宁可略微放宽也不全部拒绝；熔断恢复后半开探测。配置中心不可用时使用本地最后一份规则快照，并带磁盘持久化，网关重启也能加载。

## 五、方案取舍

| 方案 | 优点 | 缺点 |
|---|---|---|
| Redis 集中式令牌桶 + 本地租约（本方案） | 全局精度较高；Redis 压力低；突发容忍好；可水平扩展 | 实现较复杂；租约滞留带来 ≤10% 误差；需要处理节点增减时的份额 |
| 每次请求直接访问 Redis（Lua） | 实现最简单，精度最高 | 120 万 QPS 需要庞大的 Redis 集群，每个请求多一次网络往返（0.5~1ms），Redis 故障会放大成全站故障 |
| 纯本地限流（阈值 ÷ 节点数） | 零网络开销，延迟最低，无外部依赖 | 节点负载不均时误限或漏限；扩缩容需要重算阈值；无法做精确的全局配额 |
| 滑动窗口日志（ZSET） | 限流精度最高，无临界突刺 | 每个请求一条记录，内存与 CPU 开销大，不适合高 QPS，仅适合低阈值的敏感接口 |
| 固定窗口计数 | 实现极简，一个 INCR + EXPIRE | 窗口边界处可能放过 2 倍流量（临界突刺），不适合严格限流，只用于日/月配额这种粗粒度计数 |
| 引入独立限流服务（RPC） | 规则与算法集中管理，网关无状态 | 多一跳网络延迟，限流服务自身成为单点与瓶颈，需再做高可用，复杂度不低于方案一 |

## 六、容灾、监控与扩展

- **容灾**：Redis 采用 Cluster，每分片一主两从，key 以 {tenant} 作为哈希标签，同一租户的 key 落在同一分片，避免大租户跨片；网关对 Redis 做熔断与本地兜底；规则快照落盘；MySQL 主从 + 每日备份；Kafka 与 ClickHouse 故障只影响报表，不影响主链路。机房级容灾采用多活，每个机房独立 Redis，租户阈值按机房流量比例拆分。
- **监控告警**：核心指标：各租户 QPS、放行/拒绝率、Redis 调用 RT 与错误率、租约命中率（本地满足的比例）、降级与熔断次数、规则版本在各节点的一致性、配额使用率。告警项：Redis P99 > 3ms、熔断触发、单租户拒绝率 > 30% 持续 5 分钟、规则版本落后 > 60 秒、配额刷盘延迟 > 5 分钟。另做每日对账：Redis 计数与 MySQL quota_usage 与网关访问日志三方比对，差异超过 0.1% 报警。
- **扩展性**：网关节点无状态，可随意扩缩容，新节点从配置中心拉取规则后即可服务；Redis 分片按租户哈希，热点租户可通过『拆桶』方式（key 加分片后缀，阈值均分）打散到多个分片；10 倍流量增长时优先增大租约 N、增加 Redis 分片，而不是改架构；新增限流维度（如按用户、按地域）只需新增 scope_type 与对应 key 规则。
- **常见坑**：1) 令牌桶用 now_ms 必须由 Redis TIME 或网关统一时间源，避免多节点时钟漂移导致补充令牌异常；2) Lua 脚本里不要使用随机与长循环；3) Redis key 必须设置过期，防止大量不活跃租户占用内存；4) 本地桶创建要用 computeIfAbsent 并设置 LRU 淘汰，避免大量恶意 appKey 撑爆内存；5) 先鉴权后限流，未通过鉴权的请求用 IP 级低阈值限流防刷。
