# scenario-20261124-01：支付回调与订单状态一致性：幂等、乱序、丢单与对账

## 一、题目

- 某电商平台接入微信/支付宝/银行卡三类支付渠道，日均支付 500 万笔，大促峰值 3000 TPS，回调峰值约 6000 QPS（渠道会重试回调）。
- 支付单成功后必须且只能入账一次，订单状态与支付单状态最终一致；不允许“用户扣了钱但订单仍是待支付”，也不允许重复发货、重复入账。
- 渠道回调可能重复、乱序、延迟数分钟，也可能完全丢失；用户可能在支付中途重复点击、切换支付方式；渠道接口可能超时，结果未知。
- 下单到支付结果可见 P99 < 2s（回调正常时）；回调丢失时最迟 10 分钟内由主动查询补偿；T+1 对账差异必须能被发现并自动/半自动修复。
- 账务数据保留 5 年，要求可审计、可追溯，每笔资金变动都有唯一流水。

## 二、整体架构

```
  用户端 ──① 下单──> [订单服务 Order] ──② 创建支付单──> [支付服务 Pay]
                                                  │
                          ③ 调用渠道下单(带 pay_no 作为商户单号)
                                                  v
                                        [渠道适配层 Channel Adapter]
                                         微信 / 支付宝 / 银行卡
                                                  │ ④ 渠道异步回调(可能重复/乱序)
                                                  v
  [网关: 验签+限流] ──> [回调接收 Notify API] ──⑤ 落回调流水(唯一键去重)──> MySQL
                                                  │ ⑥ 立即返回 SUCCESS 给渠道
                                                  v
                                   [支付状态机 PayStateMachine]
                    ⑦ 本地事务: CAS 更新支付单 + 写 outbox(支付成功事件) + 写账务流水
                                                  │
                          [Outbox 搬运器 Relay] ──⑧ 投递──> [MQ: pay_result_topic]
                                                  │
                  ┌───────────────┬───────────────┴───────────────┐
                  v               v                               v
          [订单服务 Order]  [账务服务 Ledger]               [积分/发货/通知]
          ⑨ CAS 待支付→已支付  ⑩ 幂等入账(唯一流水号)         各自幂等消费

  兜底链路:
  [补偿查询 Job] 扫描"支付中且超过 N 秒"的支付单 ──> 主动调用渠道查单 ──> 走同一个状态机
  [T+1 对账 Job] 下载渠道账单 ──> 与 pay_order 比对 ──> 写 reconcile_diff ──> 自动修复/人工工单
  [关单 Job]     超时未支付 ──> 先向渠道查单/关单 ──> 再把支付单置为已关闭
```

## 三、关键表设计

```sql
CREATE TABLE t_order (
  id            BIGINT UNSIGNED NOT NULL COMMENT '雪花ID',
  order_no      VARCHAR(32)  NOT NULL COMMENT '订单号',
  user_id       BIGINT UNSIGNED NOT NULL,
  amount        BIGINT       NOT NULL COMMENT '应付金额，单位分',
  status        TINYINT      NOT NULL DEFAULT 0 COMMENT '0待支付 1已支付 2已关闭 3退款中 4已退款',
  pay_no        VARCHAR(32)  NULL COMMENT '最终成功的支付单号',
  version       INT          NOT NULL DEFAULT 0,
  expire_at     DATETIME     NOT NULL COMMENT '支付截止时间',
  created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_order_no (order_no),
  KEY idx_user_created (user_id, created_at),
  KEY idx_status_expire (status, expire_at)
) ENGINE=InnoDB;

CREATE TABLE t_pay_order (
  id            BIGINT UNSIGNED NOT NULL,
  pay_no        VARCHAR(32)  NOT NULL COMMENT '本系统支付单号，作为渠道商户单号',
  order_no      VARCHAR(32)  NOT NULL,
  user_id       BIGINT UNSIGNED NOT NULL,
  channel       TINYINT      NOT NULL COMMENT '1微信 2支付宝 3银行卡',
  amount        BIGINT       NOT NULL,
  status        TINYINT      NOT NULL DEFAULT 0 COMMENT '0初始 1支付中 2成功 3失败 4已关闭',
  channel_trade_no VARCHAR(64) NULL COMMENT '渠道交易号',
  success_at    DATETIME     NULL,
  next_check_at DATETIME     NULL COMMENT '下次主动查单时间',
  check_times   TINYINT      NOT NULL DEFAULT 0,
  version       INT          NOT NULL DEFAULT 0,
  created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_pay_no (pay_no),
  UNIQUE KEY uk_channel_trade (channel, channel_trade_no),
  KEY idx_order_no (order_no),
  KEY idx_status_check (status, next_check_at)
) ENGINE=InnoDB;

CREATE TABLE t_pay_notify_log (
  id            BIGINT UNSIGNED NOT NULL,
  channel       TINYINT      NOT NULL,
  notify_id     VARCHAR(64)  NOT NULL COMMENT '渠道通知ID，无则用 channel_trade_no+状态 拼接',
  pay_no        VARCHAR(32)  NOT NULL,
  raw_body      MEDIUMTEXT   NOT NULL COMMENT '原始报文，便于审计与重放',
  sign_ok       TINYINT      NOT NULL,
  handle_status TINYINT      NOT NULL DEFAULT 0 COMMENT '0待处理 1已处理 2忽略(重复/乱序)',
  created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_channel_notify (channel, notify_id),
  KEY idx_pay_no (pay_no)

CREATE TABLE t_outbox (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  biz_key       VARCHAR(64)  NOT NULL COMMENT '如 pay_no，用作 MQ 分区键',
  topic         VARCHAR(64)  NOT NULL,
  payload       JSON         NOT NULL,
  status        TINYINT      NOT NULL DEFAULT 0 COMMENT '0待发送 1已发送',
  retry_times   INT          NOT NULL DEFAULT 0,
  created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_status_id (status, id)
) ENGINE=InnoDB;

CREATE TABLE t_ledger_entry (
  id            BIGINT UNSIGNED NOT NULL,
  entry_no      VARCHAR(48)  NOT NULL COMMENT '幂等流水号 = 业务类型+pay_no，如 PAY_xxx / REFUND_xxx',
  account_id    BIGINT UNSIGNED NOT NULL,
  direction     TINYINT      NOT NULL COMMENT '1借 2贷',
  amount        BIGINT       NOT NULL,
  biz_type      TINYINT      NOT NULL,
  pay_no        VARCHAR(32)  NOT NULL,
  created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_entry (entry_no, account_id, direction),
  KEY idx_pay_no (pay_no),
  KEY idx_account_time (account_id, created_at)
) ENGINE=InnoDB;

CREATE TABLE t_reconcile_diff (
  id            BIGINT UNSIGNED NOT NULL,
  bill_date     DATE         NOT NULL,
  channel       TINYINT      NOT NULL,
  channel_trade_no VARCHAR(64) NOT NULL,
  pay_no        VARCHAR(32)  NULL,
  diff_type     TINYINT      NOT NULL COMMENT '1渠道有我方无 2我方有渠道无 3金额不符 4状态不符',
  handle_status TINYINT      NOT NULL DEFAULT 0 COMMENT '0待处理 1已自动修复 2人工处理中 3已完结',
  remark        VARCHAR(255) NULL,
  created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_diff (bill_date, channel, channel_trade_no, diff_type)
) ENGINE=InnoDB;
```

## 四、核心流程

### 一、发起支付（创建支付单）

订单服务校验订单为待支付且未过期，调用支付服务创建支付单。同一订单允许存在多个支付单（用户换渠道），但同一订单同一时刻只允许一个“支付中”的支付单：创建前先对订单加分布式锁或以订单 version 做 CAS，已有支付中的支付单则复用或先向渠道关闭旧单。pay_no 由服务端生成并作为渠道商户单号，渠道侧自带“商户单号唯一”的幂等保证，因此用户重复点击、网络重试都不会产生两笔渠道交易。支付单先落库为“初始”，调用渠道下单成功后置为“支付中”并写入 next_check_at（如 30 秒后）。渠道调用超时视为结果未知，不置失败，保持“支付中”交给补偿查询。

### 二、接收回调（只做三件事，快进快出）

1）验签并校验金额、商户号、pay_no 是否存在，失败只记录日志不处理；2）把原始报文插入 t_pay_notify_log，唯一键 (channel, notify_id) 冲突说明是重复回调，直接返回 SUCCESS；3）插入成功后同步进入状态机处理，处理成功后返回 SUCCESS。任何不确定的异常返回失败让渠道重试，因为后面全链路幂等，重试是安全的。回调接口不做任何跨服务同步调用，避免渠道超时重试放大压力。

### 三、状态机推进（本地事务 + CAS）

状态只允许单向流转：初始→支付中→成功/失败/已关闭，成功为终态。处理成功回调时在同一个本地事务内完成三步：UPDATE t_pay_order SET status=2, channel_trade_no=?, success_at=now(), version=version+1 WHERE pay_no=? AND status IN (0,1)，影响行数为 0 说明已被处理或已终态，直接按幂等成功返回；写一条 outbox 记录（支付成功事件，biz_key=pay_no）；写入账务流水（entry_no=PAY_pay_no，唯一键保证只入账一次）。乱序场景：先收到“失败/关闭”后收到“成功”时，因为渠道已扣款，必须允许 已关闭/失败 → 成功 的修正（金额以渠道为准），并触发订单侧的“已关闭订单收到支付”流程：订单已关闭则自动发起退款。反之已成功后再收到失败通知，一律忽略并告警。

### 四、下游消费（订单、账务、发货）

Outbox 搬运器按 id 顺序扫描待发送记录投递到 MQ，以 pay_no 为分区键，发送成功后置已发送，至少一次投递。订单服务消费后执行 UPDATE t_order SET status=1, pay_no=? WHERE order_no=? AND status=0；影响行数为 0 时再查一次订单当前状态：已是已支付且 pay_no 一致则幂等成功；订单已关闭则走“超时支付退款”流程；订单已被另一个支付单支付成功（重复支付）则对本笔自动退款。其他下游同理，都以 pay_no 为幂等键。

### 五、补偿查单（应对回调丢失）

补偿 Job 扫描 status=1 且 next_check_at<=now() 的支付单（走 idx_status_check），主动调用渠道查单接口，拿到成功/失败结果后调用与回调完全相同的状态机入口，因此不会出现两套逻辑。查询间隔采用递增退避：30s、1m、2m、5m、10m，之后降低频率直到超过订单过期时间；超过上限仍未知的转人工并告警。扫描按 id 取模分片给多个实例，用 SELECT ... LIMIT 批量取，避免大事务。

### 六、关单与超时支付

订单超时关闭前，必须先对其“支付中”的支付单向渠道查单：若已成功则走成功流程，若未成功则调用渠道关单接口并等待确认，然后才把订单置为已关闭。关单与支付成功都通过 CAS 更新订单状态，二者互斥，谁先成功谁生效；落败方（例如关单后又收到成功）转入自动退款，保证资金不悬挂。

### 七、T+1 对账

每日凌晨下载渠道账单文件，按渠道交易号与 pay_order 逐笔比对，分四类差异写入 t_reconcile_diff：渠道有我方无（补单或退款）、我方有渠道无（核实后置失败并告警）、金额不符、状态不符。可自动修复的类型（如渠道成功我方支付中）直接调用状态机；其余生成工单。对账结果同时校验账务流水：同一 pay_no 借贷必须平衡、金额等于支付单金额。

## 五、方案取舍

| 方案 | 优点 | 缺点 |
|---|---|---|
| 回调落库去重 + 状态机 CAS + Outbox（本方案） | 幂等边界清晰；回调快速响应；本地事务保证“状态+事件+账务”原子；下游可独立扩展；补偿与回调共用一套逻辑，易验证 | 多一张 outbox 表和搬运器，消息有秒级延迟；需要维护状态机的乱序规则 |
| 回调里同步调用订单、账务等下游（RPC 串联） | 实现最简单，代码路径短 | 任一下游超时导致回调超时，渠道重试风暴；跨服务无事务，容易订单已更新而账务失败，出现长期不一致 |
| 分布式事务 2PC/XA 或 Seata AT 横跨订单与支付库 | 强一致，业务代码少 | 吞吐低，长事务持锁，渠道回调高峰易拖垮数据库；渠道调用本身无法纳入事务，仍需补偿，收益有限 |
| 只依赖回调，不做主动查单 | 实现最少 | 回调丢失或渠道故障时订单永久待支付，用户被扣款无感知，客诉与资金风险高 |
| 基于 Redis 分布式锁做回调幂等 | 读写快 | 锁过期、主从切换会失效，不能作为资金幂等的最后一道防线；应以数据库唯一键和 CAS 为准，Redis 最多作为前置削峰 |
| TCC（Try-Confirm-Cancel） | 业务层可控，资金预留语义明确 | 渠道侧不支持 Try/Cancel 语义，改造成本高；本场景用“状态机 + 最终一致 + 对账”更贴合 |

## 六、容灾、监控、扩展性

### 容灾

数据库主从半同步，支付库按 pay_no 哈希分库分表（如 16 库 × 16 表），订单库按 user_id 分库，回调通过 pay_no 路由到分片；回调接收层无状态可水平扩容，并按渠道做独立线程池与限流舱壁，单渠道故障不拖垮其他渠道；MQ 不可用时 outbox 积压在库里不丢，恢复后自动追平；渠道整体不可用时对该渠道熔断并在收银台隐藏。机房级故障依赖同城双活 + 异地备份，回调域名通过 DNS/网关切换，渠道重试窗口（通常 24 小时内多次）可覆盖切换时间。

### 监控

核心指标：回调接收 QPS、验签失败率、重复回调率、状态机 CAS 冲突率、“支付中”超过 5 分钟的支付单数、outbox 积压条数与最老记录年龄、补偿查单成功率、订单与支付单状态不一致数（每 5 分钟巡检 SQL）、对账差异数与未处理时长。告警分级：资金类差异（我方有渠道无、金额不符）立即电话告警；积压和延迟类短信告警。全链路带 pay_no 作为 TraceId 便于排查。

### 扩展性

新增渠道只需实现适配层接口（下单、查单、关单、验签、账单解析），状态机与表结构不变；支付单按 pay_no 分片，订单按 user_id 分片，二者靠 order_no 关联并通过 MQ 解耦；回调流水表和 outbox 按月分区，历史归档到冷存储；大促前对补偿 Job 与 Relay 做压测，并预留 3 倍扩容能力。

### 安全与审计

回调必须验签并校验商户号、金额，防止伪造回调；原始报文完整留存；账务流水只追加不更新，更正通过冲正流水完成；所有人工修复操作走工单并记录操作人。
