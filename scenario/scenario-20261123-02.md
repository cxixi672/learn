# scenario-20261123-02：亿级用户站内通知 / 动态推送系统（推拉结合）

## 一、题目

- 2 亿注册用户，DAU 5000 万，在线长连接峰值约 800 万。
- 内容发布峰值 2000 条/秒；99% 的发布者粉丝数小于 1 万，但存在粉丝数达 2000 万的大 V（约 3000 个）。
- 在线粉丝需在 10 秒内收到“有新动态”提示；离线用户登录后能拉取完整收件箱，按时间倒序分页。
- 同一条动态不能给同一用户重复投递；允许少量延迟，但不允许丢失（至少一次投递 + 幂等去重）。
- 支持未读数、已读标记；收件箱保留最近 30 天。
- 大 V 发布不能拖垮系统：不能因为 1 个大 V 发 1 条动态就产生 2000 万次写入风暴。

## 二、整体架构

```
 发布者 ──> [发布服务 Publish API]
              | ① 写发件箱 notice_message (MySQL) + 发 MQ(msg_id)   ← 本地消息表保证二者一致
              v
        [MQ: publish_topic]
              |
              v
        [扇出调度 Fanout Scheduler]
          |  查发布者粉丝数 (Redis 缓存 follower_cnt)
          |
          |-- 粉丝数 < 1万 (普通号：写扩散) ---------------------+
          |      按粉丝分片(每片1000人)拆成 fanout_task          |
          |      发 MQ: fanout_topic (key = task 分片)           |
          |                                                      v
          |                                         [扇出 Worker 集群]
          |                                           ② 批量写 user_inbox (MySQL 分库分表)
          |                                           ③ 写 Redis ZSET inbox:{uid} (保留最近500条)
          |                                           ④ Redis INCR unread:{uid}
          |                                           ⑤ 在线用户 -> 推 Push 网关
          |
          |-- 粉丝数 >= 1万 (大V：读扩散) ----------------------+
                 只写发件箱 + 更新 Redis big_outbox:{bigId} ZSET
                 仅对"在线"粉丝推轻量提示 (按在线路由表分片广播)
                                                               |
 用户端 <== 长连接 ==== [Push 网关集群] <== 在线路由 Redis (uid -> gateway)
   |
   | ⑥ 拉取收件箱: GET /inbox?cursor=&size=20
   v
 [Inbox 读服务]
   合并 = 自己的收件箱(user_inbox/ZSET)  +  所关注大V的发件箱(big_outbox ZSET)
   按 msg_id 归并排序，msg_id 为雪花ID，天然有时间序
```

## 三、关键表设计

```sql
-- 1. 发件箱（所有动态主体，按 sender_id 分库分表）
CREATE TABLE notice_message (
  msg_id      BIGINT       NOT NULL COMMENT '雪花ID，趋势递增',
  sender_id   BIGINT       NOT NULL,
  msg_type    TINYINT      NOT NULL COMMENT '1动态 2点赞 3系统通知',
  content     JSON         NOT NULL,
  status      TINYINT      NOT NULL DEFAULT 0 COMMENT '0待扇出 1扇出中 2完成 3已撤回',
  created_at  DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (msg_id),
  KEY idx_sender_msg (sender_id, msg_id DESC)
) ENGINE=InnoDB;

-- 2. 收件箱（仅普通号写扩散落地；按 user_id 分 64库×16表，保留30天）
CREATE TABLE user_inbox (
  user_id     BIGINT       NOT NULL,
  msg_id      BIGINT       NOT NULL,
  sender_id   BIGINT       NOT NULL,
  is_read     TINYINT      NOT NULL DEFAULT 0,
  created_at  DATETIME     NOT NULL,
  PRIMARY KEY (user_id, msg_id),          -- 主键即幂等去重键，重复投递 INSERT IGNORE
  KEY idx_user_unread (user_id, is_read, msg_id)
) ENGINE=InnoDB;

-- 3. 用户关注的大V（用于读扩散时合并），按 user_id 分片
CREATE TABLE user_follow_big (
  user_id     BIGINT NOT NULL,
  big_id      BIGINT NOT NULL,
  last_read_msg_id BIGINT NOT NULL DEFAULT 0 COMMENT '已读到该大V的哪条，用于计算未读',
  PRIMARY KEY (user_id, big_id),
  KEY idx_big (big_id)
) ENGINE=InnoDB;

-- 4. 扇出任务（断点续传、幂等、进度监控）
CREATE TABLE fanout_task (
  task_id     BIGINT   NOT NULL AUTO_INCREMENT,
  msg_id      BIGINT   NOT NULL,
  shard_no    INT      NOT NULL COMMENT '粉丝分片号，每片约1000人',
  status      TINYINT  NOT NULL DEFAULT 0 COMMENT '0待处理 1完成 2失败',
  retry_cnt   INT      NOT NULL DEFAULT 0,
  updated_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (task_id),
  UNIQUE KEY uk_msg_shard (msg_id, shard_no),
  KEY idx_status_time (status, updated_at)
) ENGINE=InnoDB;

-- 5. 本地消息表（发布服务，保证 落库 与 发MQ 一致）
CREATE TABLE outbox_event (
  id          BIGINT AUTO_INCREMENT PRIMARY KEY,
  msg_id      BIGINT NOT NULL,
  sent        TINYINT NOT NULL DEFAULT 0,
  created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY idx_sent (sent, id)
) ENGINE=InnoDB;
```

## 四、核心流程

1. **发布**：发布服务在同一个本地事务里写 notice_message 和 outbox_event，定时任务/binlog 订阅把 outbox_event 投递到 publish_topic，保证“落库成功必有消息”。MQ 消费端以 msg_id 幂等。
2. **分流**：扇出调度读取发布者粉丝数（Redis 缓存，异步校正）。小于 1 万走写扩散；达到阈值走读扩散。阈值通过配置中心动态调整，并给出缓冲区（8000~12000）避免粉丝数在阈值附近抖动导致两种模式反复切换。
3. **写扩散**：按粉丝 ID 范围拆成每片 1000 人的 fanout_task，一个任务一条 MQ 消息。Worker 拉取该片粉丝列表，批量 INSERT IGNORE 写 user_inbox（主键 user_id+msg_id 天然幂等），同时 ZADD 到 Redis inbox:{uid}（只保留最新 500 条）并 INCR unread:{uid}。完成后把 fanout_task 置为完成，失败重试 3 次后落入死信并报警。
4. **在线提示**：Worker 通过在线路由表（Redis Hash：uid 对应网关节点）按网关节点聚合，向各 Push 网关批量发送“有新消息”轻提示，网关经长连接下发。提示只带 msg_id 和未读数，不带正文，客户端收到后再拉取，因此丢提示不丢数据。
5. **读扩散**：大 V 发布只写发件箱，并 ZADD 到 Redis big_outbox:{bigId}（保留最近 1000 条）。在线粉丝的提示由推送层按网关节点广播一条“大V有更新”事件，由网关本地匹配该节点上关注该大V的用户，避免 2000 万次点对点写。
6. **拉取**：GET /inbox?cursor=&size=20：先从 Redis inbox:{uid} 取自己的收件箱，再取该用户关注的大 V（最多取最近活跃的 200 个）的发件箱片段，在 Inbox 读服务内按 msg_id 归并排序，返回下一页 cursor（上一页最小 msg_id）。Redis 未命中时回源 MySQL，并回填缓存。
7. **未读与已读**：普通号未读数 = Redis unread:{uid}；大V未读 = 各大 V 发件箱中 msg_id 大于 last_read_msg_id 的条数。已读时批量更新 user_inbox.is_read 和 user_follow_big.last_read_msg_id，并重置计数。unread 每日由 MySQL 校正，修正 Redis 漂移。
8. **撤回与清理**：发布者撤回时将 notice_message.status 置 3，读取时过滤；user_inbox 按 created_at 做月度分区或定时批量删除 30 天前数据（每批 1000 行，避免长事务）。

## 五、方案取舍

| 方案 | 优点 | 缺点 |
|---|---|---|
| 纯写扩散（所有人都 push 到收件箱） | 读极快，逻辑简单 | 大V发一条写 2000 万行，峰值写放大严重、延迟高，还会写入大量从不登录用户的无用数据 |
| 纯读扩散（所有人都拉） | 写成本最低，无写放大 | 读时要聚合所有关注者的发件箱，关注数多时 N 次查询，P99 难保证 |
| 推拉结合 + 大V阈值（本方案） | 读写开销均衡，大V不产生风暴 | 需要维护阈值与两套路径，合并读取实现更复杂，阈值附近需缓冲防抖 |
| 只对活跃用户写扩散，其余登录时重建 | 大幅节省写入与存储 | 需要精确的活跃度判断，冷用户首次登录要承担重建延迟；可作为本方案的后续优化 |
| MQ 直接携带全量粉丝列表 | 实现简单 | 单消息体积过大，失败后无法断点续传；本方案按 1000 人一片拆任务，可重试可观测 |

## 六、容灾、监控、扩展性

- **容灾**：Redis 只做缓存和加速，数据以 MySQL 为准，Redis 整体故障时降级回源 MySQL（限流保护）；MQ 双机房部署，消费者靠 fanout_task + 主键幂等实现至少一次；Push 网关节点宕机后客户端重连并重新注册路由，同时在重连时主动拉一次增量；大 V 扇出异常时可单独熔断，其他普通号链路不受影响。
- **监控**：核心指标：发布到入箱的端到端延迟 P99（目标 10s 内）、MQ 积压量、fanout_task 失败率和待处理数、Push 网关连接数与下发成功率、Redis 命中率与内存、user_inbox 单库写入 TPS 和慢 SQL、未读数 Redis 与 MySQL 的校正差异。告警：积压持续 5 分钟增长、死信非空、延迟 P99 超标。
- **扩展性**：user_inbox 按 user_id 一致性哈希分库分表，扩容时双写迁移；扇出 Worker 无状态，按 MQ 分区数水平扩展；Push 网关按连接数水平扩展，在线路由表用 Redis Cluster 分片；热点大 V 的 big_outbox 做本地缓存 + 多副本读；写入高峰通过 MQ 削峰，而不是同步放大。
