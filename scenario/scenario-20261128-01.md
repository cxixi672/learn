# scenario-20261128-01：云盘大文件上传：分片直传、断点续传、秒传去重与安全回收

## 一、题目

**业务背景**：某云盘的旧系统让所有上传流量经过应用服务器再写入对象存储，大文件中断后只能从头传；秒传只比对客户端上报的 MD5，出现过"拿到哈希就能把别人的文件存进自己网盘"的越权；文件删除靠一个引用计数字段，计数漂移导致仍被引用的对象被清掉。现要求重新设计上传、去重与存储回收链路。

**需求约束**

- 用户：注册 1 亿，DAU 1000 万。
- 上传：日均 2000 万个文件，平均 5MB（逻辑 100TB/天），90% 小于 16MB，单文件最大 50GB；上传初始化峰值 1500 QPS；秒传后实际上行带宽峰值约 25Gbps。
- 读：目录列表峰值 3 万 QPS，P99 < 100ms；下载链接签发峰值 1 万 QPS，P99 < 50ms。
- 存量：用户文件记录 100 亿条，物理对象 60 亿个。
- 体验：弱网可断点续传，上传会话有效期 7 天；已有内容支持秒传。
- 一致性：上传完成接口返回成功后立即可见可下载；个人空间配额不可超卖；仍被引用的对象绝不能删除，无引用对象允许延迟回收。
- 安全：仅知道文件哈希不能获得文件内容。
- 可用性 99.95%，数据可靠性依托多可用区对象存储。
- 范围外：多端同步冲突、协同编辑、分享链接权限细节。

## 二、整体架构

```
[控制面: 元数据]

  Client ---> API Gateway ---> Upload Service / File Service
                                  |                |
                                  v                v
                     User Cluster (MySQL)     Content Cluster (MySQL)
                     shard = user_id          shard = hash(size, sample_hash)
                       user_file                file_object
                       upload_session           content_index
                       user_quota               object_ref
                       outbox_event
                           | outbox relay          ^
                           v                       |
                        Kafka  ---> Verify Worker -+    全量重算哈希, 通过后才可被秒传
                          |   ---> Ref Worker -----+    删除引用
                          |   ---> Scan Worker ----+    病毒与内容安全
                                                   |
                     GC Worker / Reconciler -------+    回收与对账

[数据面: 文件字节, 不经过应用服务器]

  Client ===== presigned PUT (single / multipart) =====> Object Storage (multi-AZ, EC)
  Client <==== signed URL, Range GET ===== CDN <======== Object Storage
                                                             ^
  Verify Worker  ----- streaming read ---------------------- +
  Upload Service ----- Range GET (proof of possession) ----- +
  GC Worker      ----- delete (soft delete 14d) ------------ +
```

**核心分工**

- 应用服务只处理元数据和签名，文件字节由客户端直传对象存储。
- User Cluster 决定"用户看到什么"，Content Cluster 决定"物理对象能否复用和删除"。
- 跨集群不做分布式事务，靠固定写入顺序保证不变式：**引用记录永远是用户文件的超集**。出错时最多多占空间，不会误删。

**容量估算（单机能力为假设值，上线前须压测）**

- 秒传按字节命中 35%：新增物理数据约 65TB/天，EC 冗余 1.5 倍后约 98TB/天，一年约 36PB。
- 带宽：65TB/天 均值约 6Gbps，峰值按 4 倍约 25Gbps。若经应用服务器中转，这部分流量要进出各一次。
- 校验：分片上传的对象需完整读一遍，峰值最多约 3GB/s，6 台万兆 Worker；SHA-256 有硬件指令时单核约 1GB/s 以上，瓶颈在网络。
- User Cluster：100 亿行 x 约 500B 约 5TB，每天新增约 10GB；1024 逻辑分片，初期 32 个主库。
- Content Cluster：约 4TB，1024 逻辑分片，初期 16 个主库。两集群峰值写事务各为数千 TPS，分片数主要由数据量决定。

## 三、数据库表设计

事务隔离级别统一使用 READ COMMITTED。file_id、upload_id 为雪花 ID；object_id 的高位内嵌 Content Cluster 逻辑分片号。

```sql
-- ========== User Cluster, 分片键 user_id ==========
CREATE TABLE user_file (
  user_id     BIGINT UNSIGNED NOT NULL,
  file_id     BIGINT UNSIGNED NOT NULL,
  parent_id   BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '0为根目录',
  name        VARCHAR(255)    CHARACTER SET utf8mb4 COLLATE utf8mb4_bin NOT NULL,
  is_dir      TINYINT         NOT NULL DEFAULT 0,
  object_id   BIGINT UNSIGNED NULL COMMENT '目录为NULL',
  file_size   BIGINT UNSIGNED NOT NULL DEFAULT 0,
  status      TINYINT         NOT NULL DEFAULT 1 COMMENT '1正常 2内容校验失败 3违规屏蔽',
  upload_id   BIGINT UNSIGNED NULL,
  deleted_at  DATETIME(3)     NULL COMMENT '非空表示在回收站',
  live_key    TINYINT GENERATED ALWAYS AS (IF(deleted_at IS NULL, 1, NULL)) STORED,
  created_at  DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at  DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (user_id, file_id),
  UNIQUE KEY uk_live_name (user_id, parent_id, name, live_key),
  UNIQUE KEY uk_upload (user_id, upload_id),
  KEY idx_list (user_id, parent_id, live_key, is_dir DESC, name),
  KEY idx_recycle (user_id, deleted_at),
  KEY idx_purge (deleted_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户目录树';

CREATE TABLE upload_session (
  user_id           BIGINT UNSIGNED NOT NULL,
  upload_id         BIGINT UNSIGNED NOT NULL,
  request_id        VARCHAR(64)     NOT NULL COMMENT '客户端幂等键',
  mode              TINYINT         NOT NULL COMMENT '1单次PUT 2分片 3秒传 4复制转存',
  status            TINYINT         NOT NULL
    COMMENT '0上传中 1待持有证明 2合并中 3完成 4终止',
  file_id           BIGINT UNSIGNED NOT NULL COMMENT '预分配',
  parent_id         BIGINT UNSIGNED NOT NULL,
  file_name         VARCHAR(255)    NOT NULL,
  file_size         BIGINT UNSIGNED NOT NULL,
  sample_hash       BINARY(32)      NOT NULL,
  sha256            BINARY(32)      NULL COMMENT '大文件可在完成时补传',
  object_id         BIGINT UNSIGNED NOT NULL,
  storage_upload_id VARCHAR(256)    NULL,
  part_size         INT UNSIGNED    NULL,
  challenge         JSON            NULL COMMENT 'nonce与随机区间',
  expire_at         DATETIME(3)     NOT NULL,
  created_at        DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at        DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (user_id, upload_id),
  UNIQUE KEY uk_request (user_id, request_id),
  KEY idx_status_expire (status, expire_at),
  KEY idx_status_updated (status, updated_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='上传会话(意图记录)';

CREATE TABLE user_quota (
  user_id        BIGINT UNSIGNED NOT NULL,
  quota_bytes    BIGINT UNSIGNED NOT NULL,
  used_bytes     BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '按逻辑大小, 含回收站',
  reserved_bytes BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '进行中的上传预占',
  updated_at     DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (user_id)
) ENGINE=InnoDB COMMENT='空间配额';

CREATE TABLE outbox_event (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  user_id       BIGINT UNSIGNED NOT NULL,
  event_type    VARCHAR(32)     NOT NULL COMMENT 'VERIFY/REMOVE_REF',
  biz_id        BIGINT UNSIGNED NOT NULL,
  payload       JSON            NOT NULL,
  status        TINYINT         NOT NULL DEFAULT 0 COMMENT '0待发送 1已发送',
  next_retry_at DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  created_at    DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  KEY idx_send (status, next_retry_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='本地消息表';

-- ========== Content Cluster, 分片键 hash(file_size, sample_hash) ==========
CREATE TABLE file_object (
  object_id    BIGINT UNSIGNED NOT NULL,
  bucket       VARCHAR(63)     NOT NULL,
  storage_key  VARCHAR(256)    NOT NULL COMMENT '随机key, 不用内容哈希命名',
  file_size    BIGINT UNSIGNED NOT NULL,
  sample_hash  BINARY(32)      NOT NULL,
  sha256       BINARY(32)      NOT NULL COMMENT 'status=0时仅为客户端声明值',
  status       TINYINT         NOT NULL DEFAULT 0
    COMMENT '0未校验 1可用 2校验失败 3删除中 4已删除',
  blocked      TINYINT         NOT NULL DEFAULT 0 COMMENT '内容安全屏蔽',
  zero_ref_at  DATETIME(3)     NULL COMMENT '引用归零时间',
  verified_at  DATETIME(3)     NULL,
  created_at   DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (object_id),
  KEY idx_gc (zero_ref_at, status),
  KEY idx_verify (status, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='物理对象';

CREATE TABLE content_index (
  file_size    BIGINT UNSIGNED NOT NULL,
  sample_hash  BINARY(32)      NOT NULL,
  sha256       BINARY(32)      NOT NULL,
  object_id    BIGINT UNSIGNED NOT NULL,
  created_at   DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (file_size, sample_hash, sha256),
  UNIQUE KEY uk_object (object_id)
) ENGINE=InnoDB COMMENT='秒传索引, 只收录服务端校验通过的对象';

CREATE TABLE object_ref (
  object_id    BIGINT UNSIGNED NOT NULL,
  file_id      BIGINT UNSIGNED NOT NULL,
  user_id      BIGINT UNSIGNED NOT NULL,
  upload_id    BIGINT UNSIGNED NOT NULL,
  created_at   DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (object_id, file_id),
  KEY idx_created (created_at)
) ENGINE=InnoDB COMMENT='引用明细, 代替计数器';
```

## 四、核心流程

### 1. 预检与初始化

接口：`POST /v1/uploads/precheck {size, sampleHash}`，`POST /v1/uploads {requestId, parentId, name, size, sampleHash, sha256?}`

- sample_hash = SHA-256(文件大小 + 头部 1MiB + 中部 1MiB + 尾部 1MiB)，不足 3MiB 取全文。
- 预检只查是否存在同 (size, sample_hash) 的候选。有候选，客户端先算全文 SHA-256 再初始化；无候选，大文件直接开传，边传边算哈希，避免 50GB 文件开传前长时间等待。
- 初始化事务：先条件预占配额，再插入会话。requestId 重复则回滚并返回原会话。

```
BEGIN;
UPDATE user_quota SET reserved_bytes = reserved_bytes + :size
 WHERE user_id = :uid AND used_bytes + reserved_bytes + :size <= quota_bytes;
-- 影响行数为 0: 空间不足, 回滚
INSERT INTO upload_session (...);
COMMIT;
```

- 模式选择：size >= 1MiB 且 content_index 完整命中且对象未屏蔽，走秒传（返回挑战）；否则 size <= 16MiB 走单次 PUT（必须带 sha256）；其余走分片，part_size = max(8MiB, ceil(size / 9000) 向上取整到 MiB)，保证不超过对象存储 1 万片上限。

### 2. 分片直传与断点续传

接口：`POST /v1/uploads/{id}/part-urls {parts:[{no, md5}]}`，`GET /v1/uploads/{id}`

- 每次批量签发 20~50 个预签名 URL，有效期 15 分钟；签名包含 Content-Length 与 Content-MD5，存储端拒收大小或内容不符的分片。
- 单次 PUT 的 URL 额外签入全文 SHA-256 校验头和 If-None-Match: *，防止完成后在有效期内用其他内容覆盖。兼容 S3 的存储对这两项支持不一，选型时必须验证。
- 客户端 3~6 路并发，指数退避重试；浏览器直传需在 CORS 中暴露 ETag。
- 续传：客户端本地保存 uploadId，查询接口调用 ListParts（每页最多 1000 条）返回已传分片，只补缺失部分；续传前核对本地文件大小、修改时间和已传分片 MD5。

### 3. 完成上传

接口：`POST /v1/uploads/{id}/complete {sha256, parts:[{no, etag}]}`（可安全重试）

1. 会话 CAS 0 到 2 并记录 sha256。已是 3 直接返回原文件；已是 2 则继续执行后续幂等步骤。
2. 分片模式：ListParts 逐片核对编号、ETag、大小，总大小必须等于声明值，再用客户端清单调用 CompleteMultipartUpload。重试遇到 NoSuchUpload 时用 HeadObject 确认对象已生成。单次 PUT 模式只做 HeadObject 核对大小。
3. Content Cluster 事务：插入 file_object（status=0）与 object_ref，主键冲突视为成功。
4. User Cluster 事务：

```
BEGIN;
UPDATE upload_session SET status = 3
 WHERE user_id = :uid AND upload_id = :up AND status = 2;   -- 必须影响 1 行
INSERT INTO user_file (...);          -- 重名则追加序号后重试整个事务
UPDATE user_quota SET reserved_bytes = reserved_bytes - :size,
       used_bytes = used_bytes + :size WHERE user_id = :uid;
INSERT INTO outbox_event (... 'VERIFY' ...);                -- 秒传与复制不需要
COMMIT;
```

提交后文件立即可见，本人可下载；通过校验前不参与秒传。

### 4. 秒传与持有证明

接口：`POST /v1/uploads/{id}/instant-proof {proof}`

- 初始化时服务端下发一次性随机 nonce 和 4 个随机区间（各 64KiB）。
- 客户端返回 proof = SHA-256(nonce + 各区间字节)。服务端对对象存储做 Range GET 计算期望值并常量时间比较。
- 只允许一次尝试，失败即终止会话、记风控，客户端改走普通上传。
- 通过后会话 CAS 1 到 2，执行加引用事务，再执行上面第 4 步的 User Cluster 事务。

```
BEGIN;  -- Content Cluster
SELECT status, blocked FROM file_object WHERE object_id = :obj FOR UPDATE;
-- 秒传要求 status = 1 且 blocked = 0; 否则回滚, 按未命中处理
INSERT INTO object_ref (object_id, file_id, user_id, upload_id) VALUES (...);
UPDATE file_object SET zero_ref_at = NULL WHERE object_id = :obj;
COMMIT;
```

- 复制与转存走同一套流程（mode=4），因已通过源文件鉴权，允许引用 status 为 0 或 1 的对象。
- 隐私：秒传结果会暴露"平台上是否有人存过该内容"。对策：小于 1MiB 不秒传、按用户限流；企业版把 tenant_id 加入 content_index 主键，只在租户内去重。

### 5. 异步校验

- Verify Worker 流式读取对象，重算 sha256 与 sample_hash，大小文件分队列，避免大文件阻塞小文件。
- 一致：事务内 status 0 改 1（条件更新），成功后插入 content_index，主键已存在则忽略。两人同时首次上传相同内容时各留一份物理对象，只有一份进索引，浪费极小，换来无需跨分片改引用。
- 不一致：置 status=2，按 object_ref 找到所有引用者，把对应 user_file 置为校验失败并提示重传。内容违规时同样按 object_ref 扇出屏蔽。
- 兜底：定时扫描超过 30 分钟仍为 status=0 的对象重新投递。

### 6. 删除与垃圾回收

- 删除先进回收站（写 deleted_at，目录只标记自身节点）。30 天后或用户清空时，异步分批遍历子树：User Cluster 事务内删除 user_file 行、扣减 used_bytes、写 REMOVE_REF 事件（目录行最后删）。
- Ref Worker 在 Content Cluster 事务内先锁 file_object 行，删除 object_ref；若该对象已无引用，写 zero_ref_at。
- GC 只处理归零超过 7 天的对象：

```
BEGIN;
SELECT status, zero_ref_at FROM file_object WHERE object_id = :obj FOR UPDATE;
-- 要求 status IN (0,1,2) 且 zero_ref_at 早于 7 天前
SELECT 1 FROM object_ref WHERE object_id = :obj LIMIT 1;    -- 必须为空
UPDATE file_object SET status = 3 WHERE object_id = :obj;
DELETE FROM content_index WHERE file_size = :size AND sample_hash = :sh
   AND sha256 = :sha AND object_id = :obj;
COMMIT;
-- 事务外删除物理对象(幂等), 再置 status = 4
```

加引用与 GC 都先锁同一行，先到者胜：秒传先到则 GC 发现有引用；GC 先到则秒传看到 status=3，退回普通上传。

### 7. 超时、卡单与对账

- 过期会话：事务内 CAS 状态（0/1/2）到 4 并释放预占配额。分片或单次模式再中止分片任务；已有 file_object 的删除引用交给 GC，没有的直接删对象 key。秒传和复制模式绝不删对象。存储侧另设 8 天自动清理未完成分片的生命周期规则。
- 卡在合并中的会话：每分钟扫描并重放第 2~4 步。
- 悬挂引用（超过 24 小时）：**先**确认会话处于终态（非终态则 CAS 为 4 并释放配额），**再**查 user_file，不存在才删引用。顺序不能反，否则可能与迟到的完成请求竞争。
- 反向对账（每天）：每条 user_file 必须有对应 object_ref，缺失按 P0 处理，立即补引用并暂停 GC。

### 8. 列表与下载

- `GET /v1/files?parentId=&cursor=&limit=100`：走主库和 idx_list，游标为 (is_dir, name)，保证写后即读。
- 移动目录：先对 user_quota 行加锁串行化同一用户的移动操作，再向上遍历祖先防止成环。
- `POST /v1/files/{fileId}/download-url`：校验归属与状态，查对象（缓存 storage_key；屏蔽时推送名单并刷新 CDN 缓存），签发 5~15 分钟 CDN 链接。CDN 边缘先鉴权，再按对象 key 缓存，支持 Range。

## 五、方案取舍

### 上传链路

| 方案 | 优点 | 缺点 |
|---|---|---|
| 预签名 URL 分片直传（采用） | 应用层不承载字节流量；权限细到单个分片；续传简单 | 客户端逻辑复杂；签名请求量增加；完整性需事后校验 |
| 应用服务器中转 | 可边传边算哈希和扫描，控制力强 | 带宽进出各一次，长连接占资源，扩容成本高 |
| 临时凭证 + SDK 直传 | SDK 成熟，签名调用少 | 权限范围难细到大小和内容；客户端绑定存储厂商 |

### 去重粒度

| 方案 | 优点 | 缺点 |
|---|---|---|
| 整文件去重（采用） | 元数据少，下载是单对象，GC 简单 | 文件改一个字节就要整份重存 |
| 固定大小分块去重 | 追加写场景复用好 | 头部插入导致后续块全部错位；元数据放大数百倍 |
| 内容定义分块（FastCDC 等） | 去重率最高，抗插入偏移 | 客户端计算重，块索引与 GC 复杂，下载需拼装 |

### 引用管理

| 方案 | 优点 | 缺点 |
|---|---|---|
| 引用明细表 + 冷静期 GC（采用） | 增删天然幂等，可追溯、可对账、可扇出屏蔽 | 多一张百亿级表，判零需查询 |
| ref_count 计数器 | 存储小，更新快 | 重试和消息重复导致漂移，且无法定位原因 |
| 离线标记清除 | 在线链路无引用维护 | 百亿级全量扫描周期长，快照与在线写入有竞争 |

### 哈希可信性

| 方案 | 优点 | 缺点 |
|---|---|---|
| 异步服务端校验后入索引（采用） | 完成接口快，且错误哈希不会污染秒传 | 多一次全量读；校验前同内容无法秒传 |
| 信任客户端哈希 | 零计算成本 | 可投毒索引，他人秒传拿到错误内容 |
| 完成接口同步校验 | 状态简单 | 大文件需几十秒到数分钟，请求易超时 |

分片上传返回的 ETag 或组合校验值不等于全文 SHA-256，不能用来替代全量校验。

### 哈希算法

| 方案 | 优点 | 缺点 |
|---|---|---|
| SHA-256（采用） | 抗碰撞，生态与硬件支持好 | 单文件只能串行计算 |
| MD5 | 快，老系统兼容 | 可构造碰撞，不能用作去重身份 |
| 树形哈希（BLAKE3 等） | 可并行，分片可独立校验后合并 | 对象存储原生校验与各端库支持较少 |

## 六、容灾、监控与扩展

### 容灾

- 误删防线共四层：写入顺序保证引用超集；7 天冷静期；GC 删除限速加熔断（单小时删除量超过 7 日均值 3 倍即暂停）和一键开关；对象存储软删除保留 14 天。
- 软删除保留期必须长于数据库可回滚窗口。任何数据库时间点恢复或切主后，先暂停该分片 GC，完成双向对账再开启。
- Content Cluster 使用 MGR 或半同步，避免丢失刚加的引用。单分片故障时秒传按未命中处理，落在该分片的完成请求返回可重试错误，会话和已传分片保留。
- User Cluster 单分片故障只影响该部分用户。
- Kafka 故障：outbox 积压，文件仍可见可下载，仅秒传命中率下降、回收延后。
- 对象存储：多可用区纠删码，重要桶跨地域复制；分片上传失败时客户端退避重试，按地域熔断切换新会话的上传桶。
- 过载保护：依次降级秒传（跳过持有证明的读开销）、延后校验与回收、限制免费用户并发分片数。

### 监控与告警

- 业务：上传成功率、初始化到完成耗时（按大小分桶）、分片重试率、秒传字节命中率、持有证明失败率（突增代表撞库）。
- 一致性（预期恒为 0）：user_file 缺引用、被引用对象在存储中不存在、used_bytes 与明细求和不符。
- 积压：最老未校验对象年龄（> 30 分钟告警）、卡在合并中的会话数、outbox 最老事件年龄。
- 成本：存储清单与 file_object 比对出的孤儿字节、待回收字节、冷热分层占比、CDN 命中率。

### 扩展

- 分库扩容：1024 逻辑分片整体迁移到新实例，object_id 内嵌逻辑分片号，路由表变更即可。
- 多地域：就近上传到本地域桶，file_object.bucket 记录归属；跨地域下载走 CDN 回源。
- 冷热分层：按对象最后访问时间由生命周期规则转低频或归档，归档对象下载前需解冻。
- 演进分块去重：只对超大且频繁改版的文件启用，file_object 增加分块清单，引用与 GC 下沉到块级。
