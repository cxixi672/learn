# scenario-20261123-01：秒杀场景下的库存扣减与订单一致性

## 一、题目

某电商平台要做一次限量商品秒杀：活动商品 1 个 SKU，库存 10,000 件，每人限购 1 件。需求如下：

- 活动开始瞬间，入口请求峰值约 50 万 QPS（含大量刷量和重复点击），真正能通过网关风控、进入下单链路的请求约 5 万 QPS。
- 库存不允许超卖；已支付订单数 + 待支付订单数 必须严格等于已扣减库存数。
- 同一用户重复点击或重放请求，不能下出两单。
- 未支付订单 15 分钟后自动关闭，库存需回补，且只能回补一次。
- 下单接口 P99 < 200ms（不含排队）；允许返回"排队中"，前端轮询结果。
- 系统需容忍 Redis 主从切换、MQ 短暂不可用、消费者重启，不能出现超卖，也不能出现库存永久少卖。
- 活动峰值订单约 1 万单，远小于日常订单量。

## 二、整体架构

```
 用户端 (App / H5)
    |  ① 活动页静态化（CDN），倒计时以服务端时间校准
    v
 [网关 Gateway]
    |  ② 黑名单 + 单用户限频 + 验证码/答题
    |    + 全局放行计数（累计放行约 3 × 库存 即关闸）
    v
 [秒杀服务 Seckill API] ---(③ Lua 原子预扣)---> [Redis Cluster]
    |                                             seckill:{act}:stock   剩余库存
    |  ④ 同步发送 MQ，失败则回滚 Redis              seckill:{act}:bought  已下单用户集合
    v
 [MQ: seckill_order_topic]   分区键 = user_id
    |  ⑤ 异步消费
    v
 [订单消费者] ---(⑥ 本地事务)---> [秒杀专用库 MySQL]
                                    seckill_order   唯一键 (activity_id, user_id)
                                    seckill_stock   条件更新 available > 0
    |
    |  ⑦ 下单成功后投递 15 分钟延迟消息
    v
 [超时关单消费者] ---> 本地事务：CAS 关单 + DB 回补 ---> Redis 幂等回补（Lua）

 [对账任务] 每分钟比较 DB 库存、订单数、Redis 库存；[监控告警]
```

说明：秒杀订单与库存放在同一个专用库中（峰值仅 1 万单），这样"扣库存 + 插订单"可以用一个本地事务完成，避免分布式事务。活动结束后再异步同步到主订单库。

## 三、表设计

```sql
-- 秒杀活动
CREATE TABLE seckill_activity (
  activity_id     BIGINT UNSIGNED NOT NULL PRIMARY KEY,
  sku_id          BIGINT UNSIGNED NOT NULL,
  price           DECIMAL(10,2)   NOT NULL,
  start_time      DATETIME        NOT NULL,
  end_time        DATETIME        NOT NULL,
  per_user_limit  TINYINT UNSIGNED NOT NULL DEFAULT 1,
  status          TINYINT         NOT NULL DEFAULT 0 COMMENT '0未开始 1进行中 2已结束',
  created_at      DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY idx_sku_start (sku_id, start_time)
) ENGINE=InnoDB;

-- 库存（热点行，单独一行一个活动）
CREATE TABLE seckill_stock (
  activity_id BIGINT UNSIGNED NOT NULL PRIMARY KEY,
  total       INT UNSIGNED    NOT NULL,
  available   INT             NOT NULL,
  version     BIGINT UNSIGNED NOT NULL DEFAULT 0,
  updated_at  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  CONSTRAINT chk_stock_nonneg CHECK (available >= 0)  -- 最后一道超卖防线（MySQL 8.0.16+）
) ENGINE=InnoDB;

-- 秒杀订单
CREATE TABLE seckill_order (
  order_id     BIGINT UNSIGNED NOT NULL PRIMARY KEY,   -- 服务端雪花 ID，随消息下发，保证重试幂等
  activity_id  BIGINT UNSIGNED NOT NULL,
  user_id      BIGINT UNSIGNED NOT NULL,
  sku_id       BIGINT UNSIGNED NOT NULL,
  amount       DECIMAL(10,2)   NOT NULL,
  status       TINYINT         NOT NULL COMMENT '0待支付 1已支付 2已关闭(超时)',
  created_at   DATETIME        NOT NULL,
  paid_at      DATETIME        NULL,
  updated_at   DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_activity_user (activity_id, user_id),  -- 限购的数据库兜底
  KEY idx_user (user_id, created_at),
  KEY idx_status_created (status, created_at)          -- 超时补偿扫描用
) ENGINE=InnoDB;
```

## 四、核心流程

**0. 预热（开始前 5 分钟）**：把库存写入 Redis `SET seckill:{act}:stock 10000`，`DEL seckill:{act}:bought`。`{act}` 为 hash tag，保证两个 key 落在同一 Redis Cluster 槽位，Lua 才能同时操作。

**1. 预扣库存（秒杀接口，原子操作）**：

```lua
-- KEYS[1] = seckill:{act}:stock     剩余库存
-- KEYS[2] = seckill:{act}:bought    已下单用户集合
-- ARGV[1] = user_id
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
  return 2                             -- 已购买（限购 1 件）
end
local stock = tonumber(redis.call('GET', KEYS[1]) or '0')
if stock <= 0 then
  return 0                             -- 售罄，不进 MQ
end
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1                               -- 预扣成功
```

Lua 在 Redis 中单线程原子执行，"判断 + 扣减 + 记录用户"不会被并发打断，是第一道防超卖。

**2. 投递消息**：返回 1 时，服务端生成 `order_id`，同步发送 MQ（分区键 `user_id`）。发送失败则同步重试 3 次；仍失败则执行回滚 `INCR stock` 与 `SREM bought`（同样用 Lua 包装），返回"系统繁忙，请重试"。

**3. 消费者落库（本地事务）**：

```sql
BEGIN;
INSERT INTO seckill_order (order_id, activity_id, user_id, sku_id, amount, status, created_at)
VALUES (?, ?, ?, ?, ?, 0, NOW());
-- 唯一键冲突（order_id 或 activity_id+user_id）=> 重复消息，ROLLBACK 后直接 ACK

UPDATE seckill_stock
SET available = available - 1, version = version + 1
WHERE activity_id = ? AND available > 0;
-- 影响行数为 0 => ROLLBACK，记录"Redis 与 DB 库存不一致"告警，ACK（交由对账修正，不无限重试）
COMMIT;
-- COMMIT 成功后 ACK MQ 消息
```

唯一键保证重复投递不会产生两单；`available > 0` 与 CHECK 约束保证 DB 侧不超卖。

**4. 查询结果**：前端轮询 `GET /seckill/result?activity_id=&user_id=`：先查订单表，若无记录且 Redis `bought` 中存在该用户，返回"排队中"；两者都没有，返回"未抢到"。

**5. 超时关单（延迟消息 15 分钟）**：

```sql
BEGIN;
UPDATE seckill_order SET status = 2
WHERE order_id = ? AND status = 0;          -- CAS：只有待支付才能关闭
-- 影响行数 = 1 时才执行下面的 DB 回补
UPDATE seckill_stock SET available = available + 1
WHERE activity_id = ?;   -- 仅当上一句影响行数为 1 时执行
COMMIT;
```

然后执行 Redis 回补（必须幂等，因为消费者可能重试）：

```lua
-- KEYS[1] = seckill:{act}:stock
-- KEYS[2] = seckill:{act}:restored:{order_id}
if redis.call('SET', KEYS[2], 1, 'NX', 'EX', 86400) then
  redis.call('INCR', KEYS[1])
  return 1
end
return 0
```

注意：已关闭订单（status=2）重复投递时，也要再执行一次 Redis 幂等回补，以覆盖"DB 已提交但 Redis 未回补就崩溃"的情况；已支付订单（status=1）则直接跳过。"限购"按下单计数，关单不释放购买资格，这一规则需要和业务方确认。

**6. 兜底补偿**：每分钟扫描 `status = 0 AND created_at < NOW() - INTERVAL 15 MINUTE` 的订单，走同样的关单流程。防止延迟消息丢失。

## 五、方案取舍

**为什么用 Redis 预扣？** 单行库存在 InnoDB 中要靠行锁串行化，单行 UPDATE 的吞吐大约只有几千 TPS，5 万 QPS 的请求直接打到 DB 上必然打满。Redis 单分片执行 Lua 可达数万到十万级 QPS，且绝大部分售罄与重复请求在这里就被拦截。

**为什么要 MQ 异步落库？** 削峰。Redis 放行的 1 万个名额会在很短时间内涌入，异步化后 DB 按消费者能力平稳写入。代价是下单结果不是同步返回的，需要轮询接口，并且要处理 MQ 发送失败的补偿。

**备选方案及缺点：**

- **直接 `UPDATE stock SET available = available - 1 WHERE available > 0`**：实现最简单、强一致、无需对账。但峰值 5 万 QPS 全部压在一行上，DB 直接被打满。适合小流量活动。
- **乐观锁 version 重试**：库存接近耗尽时冲突率急剧上升，大量 CAS 失败触发重试风暴，实际吞吐反而低于悲观的行锁方案。
- **Redis 预扣 + 同步写 DB（不走 MQ）**：链路变长，接口 RT 受 DB 限制，失败时需要同步回滚 Redis，异常分支复杂，仍然要 DB 兜底。
- **库存分段预分配**（每个应用实例从 Redis 批量领取一段库存本地扣减）：性能最高，适合百万级 QPS，但要处理段回收、碎片库存导致的少卖。本题规模不需要。
- **秒杀订单与主订单库分开**：这是本方案的关键取舍。代价是活动后要同步数据，收益是免去跨库分布式事务，"扣库存 + 插订单"变成一个本地事务，并且 `uk_activity_user` 唯一键才能真正生效。

## 六、容灾、监控与扩展性

**容灾**

- **Redis 主从切换丢数据**：Redis 开启 AOF（everysec），关键写入使用 `WAIT` 等待至少一个从库确认。切换后先关闭放行（新请求返回"排队中"），等 MQ 中的在途消息消费完，再以 DB 为准重建：`stock = seckill_stock.available`，`bought` 由 `seckill_order` 中该活动的 user_id 全量重建。重建完成后恢复放行。
- **MQ 不可用**：发送失败立即回滚 Redis 并返回繁忙；错误率超过阈值时网关熔断，活动页降级为"活动火爆，请稍后再试"。
- **消费者宕机或重启**：消息留在 MQ 中不丢，依赖唯一键做幂等。
- **DB 故障**：消费者指数退避重试，消息在 MQ 中堆积；订单状态不变，最多是出结果变慢，不会超卖。
- **防刷**：网关层做验证码或答题、设备指纹、IP 与用户双维度限频；全局放行计数限制进入扣减链路的请求量（约 3 倍库存）。
- **延迟消息丢失**：由第 6 步的定时补偿兜底。

**监控**

- **库存一致性（核心）**：`seckill_stock.available >= 0`（违反即 P0 告警）；每分钟校验 `total - available = 已支付订单数 + 待支付订单数 + 已关闭后已回补的部分`，即 `total = available + (status 0 或 1 的订单数)`；Redis `stock` 与 DB `available` 的差值减去 MQ 堆积量，持续非 0 超过 3 分钟触发 P1 告警。
- **业务指标**：下单成功、售罄、已购、繁忙各自占比；MQ 堆积量与消费延迟；Lua 耗时；接口 P99；网关拦截数。
- **补偿指标**：超时关单数与回补数是否一致；每分钟补偿任务实际修复的订单数（应接近 0，偏高说明延迟消息链路有问题）。

**扩展性**

- **多 SKU 活动**：Redis key 以 `{act}` 为 hash tag 分散到不同分片，不同活动互不影响。
- **单 SKU 超热点**：库存拆为 N 个子 key（`seckill:{act}:stock:{0..N-1}`），用户按 hash 路由到子 key，售罄判断需要轮询子 key，或者在放行层就限制每个子 key 的放行量。
- **消费者水平扩展**：MQ 分区数不少于消费者实例数。本题订单量小，DB 写入不会成为瓶颈。
- **活动收尾**：异步把秒杀订单同步到主订单库，清理 Redis 中活动相关 key，并对最终库存做一次全量对账。
